# /release — опубликовать релиз на GitHub

Владелец просит выпустить новую версию. Это **необратимое внешнее действие** (публичный тег +
GitHub Release). Выполни процедуру **по порядку**; проговаривай каждый шаг в чате. Если шаг падает — остановись,
покажи ошибку, НЕ продолжай вслепую.

> ⚠️ **ТРЕБУЕТСЯ ПОДТВЕРЖДЕНИЕ.** Перед самой публикацией покажи владельцу: какая будет версия
> (текущая → новая), что дерево чистое, что собралось. Публикуй только по его явному «да». Релиз
> = публичный тег и Release, откатывать неприятно. **В автономном режиме (`/autoloop`/циклы) НЕ
> публикуй релиз.**

## Шаг 0. Определи тип поднятия версии и кодовое имя (стоп ИДЕНТИЧНОСТИ, не формальность)

Подтверди с владельцем (или подтверди дефолт): patch / minor / major. Назови текущую → новую версию.

**У релиза обычно есть короткое кодовое имя** (запоминающееся название темы в 1–2 слова, напр.
*Anonymous*, *Slim*, *Savvied*). Кодовое имя задаёт **заголовок** релиза и его хедлайн — см. Шаг 6.

**Кодовое имя — ИДЕНТИЧНОСТЬ, а идентичность авторизует только владелец — никогда агент, ни при
каком объёме одобрения.** Бланковое «отгружай, меня не спрашивай» снимает ФРИКЦИЮ ПОДТВЕРЖДЕНИЙ на
действия — оно не передаёт АВТОРСТВО того, как продукт себя предъявляет (полевой инцидент: под
дословным «НА ВСЁ ДАЮ ДОБРО, не спрашивай» агент сам придумал кодовое имя релиза, и владелец
увидел имя своего продукта как свершившийся факт). У жёсткого стопа ровно три легальных исхода:

1. **имя даёт владелец** (или выбирает из предложенных тобой кандидатов);
2. **сделай ВСЁ остальное и задай ОДИН точечный вопрос про имя** — один вопрос внутри уже
   разрешённой работы не стоит ничего, и «не спрашивай» было не про него;
3. **релиз БЕЗ имени** нейтральным фактическим заголовком (`<PROJECT> X.Y`) — ВСЕГДА ДОСТУПНЫЙ
   запасной выход: владелец недоступен → релиз не блокируется навсегда, а имя вправе дать только
   владелец, хоть задним числом (решение №28). Но никогда не имя-заглушка: заглушка — тоже имя,
   которое кому-то придётся отменять.

**У отгруженного имени — АРТЕФАКТ ИСТОЧНИКА**: строка в нотах/плане релиза
`кодовое имя: <владелец · канал · дата>` — как у исследовательского утверждения ссылка; имя без
автора обязано быть видно. И если отгруженное имя оказалось ошибкой — агент не переименовывает по
своей инициативе: исправление брендовой ошибки — тоже брендовое решение.

## Шаг 1. Предпроверка окружения (не релизь на грязном/сломанном дереве)

```bash
git status --short          # дерево должно быть ЧИСТЫМ (кроме gitignore-артефактов)
git branch --show-current   # релизная ветка (например, main)
git pull --rebase           # чтобы пуш был fast-forward
gh auth status              # gh залогинен (нужно для GitHub Release)
```
Если дерево грязное — сначала закоммить/разберись (`/pause` или твой инструмент коммита).

Проект ведёт **реестр пар «истина↔зеркало»** (`AGENT_GUIDE.md` → Гигиена документов и текста) —
прогони команду сверки каждой строки сейчас: релиз поверх разъехавшейся пары вшивает дрейф в
поставку. Красная строка = стоп и сведение до продолжения. Рядом — страж места вопросов:
`node tools/questions-guard.mjs` (красное = стоп: вопрос владельцу вне `interviews/` или
неразнесённый ответ не должны уехать в релиз).

## Шаг 2. Обнови README (все языки)

Приведи `README.md` в соответствие с реальностью: статус фаз, рабочие фичи, инструкции. Если двуязычный, держи
обе версии синхронными. Не выдумывай — отражай только то, что действительно сделано и проверено (сверься со
`STATUS.md` и закрытыми `bugs/`/`ideas/` `*_DONE_*`).

**README и релиз-ноты — АРТЕФАКТЫ ВЛАДЕЛЬЦА, витрина, которую он подписывает.** Есть портрет
голоса (`AUTHOR_STYLOMETRY.md`, навык `/owner-voice`) — ОТКРОЙ его сейчас и прогони его чек-лист
перед сдачей текста; портрета нет — обязанности нет, и его отсутствие релиз не красит. Портрет
ЧЕРНОВОЙ (пороги не добраны, слепой тест не пройден) — по нему ПИШУТ, но им не ПЕРЕПЕВАЮТ: режим
`rewrite` от черновика не стартует. В любом случае вердикт «это мой голос» выносит владелец —
класс «вкус» агентом не судится (`TESTING_FRAMEWORK.md`).

**Сверка версий слепка** (решение №62): `node tools/stylometry-snapshot.mjs --version-check` —
печатает одну строку, если слепок отстал от приватного ядра, и завершается кодом 0. Она
КОНСТАТИРУЕТ и ничего не требует: обновление — только по явному слову владельца.

## Шаг 4. Контрольная сборка (перед релизом)

`<Запусти сборку проекта (BUILD_COMMAND). Она должна пройти успешно. Это ловит ошибки ДО поднятия версии, чтобы
не оставить полу-выпущенную версию.>`

**Шаг 4.1 (специфика истока KAIF): TEMPLATE_NOTES описывают ЭТОТ релиз.** Перепиши
`TEMPLATE_NOTES` в `tools/build-framework.mjs` под содержание выпускаемой версии и проставь
`codename` в `version.json` — заметки шаблонов и есть инструкция по слиянию для обновляющихся
проектов; протухшие заметки — самый массовый полевой дефект 1.6 (bugs/10, 6 отчётов из 8).
Страж в `check-framework.mjs` валит сборку, если заметки не называют собственную версию, — но
свежесть ПРОЗЫ (пункты описывают именно этот релиз) проверяешь ты, страж прозу не судит.

## Шаг 4.5. Judge-проход — ОБЯЗАТЕЛЬНАЯ адверсарная проверка перед публикацией

Прогони `/fable-judge` по заявлениям самого релиз-кандидата: каждое утверждение README/нот о том, что
работает, перепрогоняется или переоткрывается (сборка, самопроверки, список артефактов, версии, ссылки),
а фактический дифф сверяется с заявленным скоупом релиза. Вердикт должен быть **VERIFIED** либо
**VERIFIED WITH CAVEATS** с каждой оговоркой, явно внесённой в ноты релиза. **REFUTED блокирует релиз** —
почини и пересуди до продолжения. (Релиз — единственный артефакт, чьи ложные заявления скачает весь мир.)

## Шаг 5. Закоммить изменения документов/сборки (перед релизом)

Закоммить обновления README/документов, чтобы коммит `release: X.Y` был чистым поднятием версии:
```bash
node tools/commit.mjs "docs: README for release X.Y"
```

## Шаг 6. Публикация (после подтверждения владельца)

`<Запусти свой релизный процесс. Если у тебя есть релизный инструмент (например, tools/release.mjs, который поднимает версию,
собирает, переименовывает артефакт, коммитит "release: X.Y", ставит тег vX.Y, пушит и запускает gh release create с
авто-нотами), запусти его. Иначе сделай это явно:>`
```bash
# подними версию (в version.json или твоём манифесте), затем:
git commit -am "release: X.Y" && git tag vX.Y && git push && git push --tags
gh release create vX.Y --title "<PROJECT> X.Y — <Кодовое имя>" --notes-file <NOTES.md> <ARTIFACT(S) if any>
```

> 📛 **Заголовок релиза — ФИКСИРОВАННЫЙ ФОРМАТ (КАНОН):** `<PROJECT> X.Y — <Кодовое имя>` — имя проекта,
> версия `major.minor`, длинное тире `—`, затем кодовое имя из Шага 0. Примеры: `KAIF 1.2 — Anonymous KAIF`,
> `KAIF 1.3 — Slim KAIF`, `KAIF 1.4 — Savvied KAIF`. На легальном БЕЗЫМЯННОМ исходе Шага 0 заголовок —
> нейтральный `<PROJECT> X.Y`: фактический, без выдуманного имени. **Не** `vX.Y`, без «ёлочек», без
> кавычек. Держи единообразие со всеми прошлыми релизами (сверься `gh release list`).
>
> 📝 **Описание релиза — ДЕЛЬТА, никогда не копия README (НЕ `--generate-notes`).** Ноты отвечают на
> ОДИН вопрос: *«что изменилось в ЭТОЙ версии и нужно ли обновляться?»* — строго дельта версии; всё,
> что описывает продукт вообще, ЛИНКУЕТСЯ на README, а не копируется (полевой инцидент: ноты на
> 34 КБ оказались почти копией README; переписаны по дельте — 12 КБ без потери единого факта).
> Механическая проверка скоупа перед публикацией: **абзац, который можно без изменений вставить в
> README, — место в README, а не в нотах.**
> **У документов разные источники вдохновения:** ноты берут форму из ПРОШЛЫХ нот ЭТОГО проекта
> (`gh release view <prev> --json body -q .body` — следуй домашнему стилю); README — из текущего
> README и соседних витрин владельца. Зеркаль **на всех языках README** с якорями/переключалкой.
> Структура на каждом языке: строка-заголовок (дата · место), абзац «что это за релиз», приложенные
> артефакты, секция **✨ Что нового** (дельта), заметка **⬆️ Обновление** где уместно, и ССЫЛКА на
> README про то, что такое продукт и как начать. Пиши ноты в файл и передавай `--notes-file`.

## Шаг 6.5. Деплой-чеклист (когда отгрузка заменяет РАБОТАЮЩУЮ систему)

Если релиз включает выкат поверх живого сервера/контейнера/сервиса — пройди пять гейтов; каждый
существует потому, что его пропуск ронял реальный прод:

1. **Сначала деплой-зеркало.** Сними ФАКТИЧЕСКУЮ конфигурацию работающего прода ДО замены
   (inspect/env/версия) — прод часто живёт с настройками, которых не помнит ни один документ, и слепой
   перевыкат «по докам» молча меняет поведение (или целит прод в дев-эмулятор). Каждое отличие нового
   запуска от старого — осознанное, названное решение.
2. **Живой смоук.** Запусти новый экземпляр и прочитай его первый рабочий цикл в логе глазами
   (`TESTING_FRAMEWORK.md` → гейты наблюдения).
3. **Самодостаточность артефакта.** Образ/бандл стартует в изоляции, все модули на месте — образ,
   отставший от кода, ронял проды при всех зелёных тестах.
4. **Инварианты домена.** До переключения выпиши числа, которые не должны измениться (счётчики, суммы,
   размеры); после — сверь.
5. **Документ «боевой запуск».** После выката обнови в репо документ о том, как прод реально запущен, —
   единственный источник правды. Прод-конфиг, живущий только в работающем процессе, — мина для
   следующей сессии.

## Шаг 7. Проверь и отчитайся

```bash
gh release view vX.Y        # релиз существует, артефакты приложены
git log --oneline -3        # коммит релиза + тег видны
```
Отчитайся владельцу: версия, ссылка на релиз, что приложено. Готово.

## Заметки
- Релизы поднимают minor/major; обычные рабочие коммиты поднимают build/patch.
- Если пуш отклонён (non-fast-forward) — `git pull --rebase` и повтори. На шаге 6 это критично:
  тег может уже существовать локально — проверь `git tag` и `git tag -d vX.Y` перед повтором.
- НИКОГДА не делай force-push и никогда не удаляй чужие теги/релизы. Если во время публикации что-то идёт не так — остановись
  и покажи владельцу, не «чини» это вслепую.
- Не релизь в автономном режиме — только по явному запросу владельца.
