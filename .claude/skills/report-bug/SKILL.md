# /report-bug — завести документ бага в bugs/ (агент ведёт свой беклог багов)

Всякий раз, когда агент пишет код, тестирует его и **натыкается на баг** (краш, неверное поведение, артефакт,
регрессия, дефект библиотеки), он заводит ОТДЕЛЬНЫЙ md-документ в `bugs/` по тем же правилам, что и
существующие документы по багам. Так агент накапливает себе беклог багов — ничего не теряется, и к любому багу
можно вернуться (или передать его в `/bug-research`).

> Правило проекта (`AGENT_GUIDE.md`): «для каждого бага, даже мелкого — отрефлексируй и зафиксируй знания в
> отдельном md в `bugs/`». Этот навык как раз это и автоматизирует.

## Когда вызывать

- Агент увидел дефект во время разработки/теста, который он НЕ чинит прямо сейчас (или чинит, но хочет
  зафиксировать форензику/постмортем).
- Баг нужно отложить (взять другую задачу), не потеряв его.
- Владелец просит завести баг.
- **Владелец упомянул баг мимоходом, пока ты работал над другим** (drive-by, идея 17 §2): заведи с
  пометкой источника («набросил владелец, <дата>»), подтверди одной строкой и вернись к текущей задаче.
- НЕ для затыка «застрял из-за непонимания» (это `PHILOSOPHY.md`) и не вместо исправления тривиальной опечатки.
- **Размер ответа сверяется до первой строки** — лестница тяжести (`BUG_FIXING_FRAMEWORK.md`):
  S1 / S2 получают документ бага со строкой `Severity:` в шапке; **S3 (заусенец, косметика,
  разовая опечатка) получает одну строку в `EXPERIENCE.md` (`/experience`) и документа НЕ заводит.**

## Ветка: дефект САМОГО ФРЕЙМВОРКА (с оговоркой истока)

В полевых проектах навык ветвится: если грабля существует из-за того, КАК сформулирован или ведёт
себя сам KAIF (руководящий док/навык/шаг машинерии увёл не туда, гейт лгал зелёным, не хватило
гвардрейла), — сигнал адресован разработчику KAIF и уходит в `bugs/KAIF/` по шаблонам
**A (bug report)** / **B (improvement request)**: обязательная аттестация дедупа (греп локального
`bugs/KAIF/` + в режиме origin-привязки — открытые issues истока; совпадение surface+symptom-class
= «+1 наблюдение» в существующий тикет, не новый), fingerprint-строка
`kaif-fp: <surface> :: <symptom-class> :: v<major.minor>`, гейт качества отправителя (в апстрим —
только с детерминированным репро ИЛИ дословной цитатой-уликой; blameless), доставка по режиму
привязки (origin — **по СТОЯЧЕЙ АВТОРИЗАЦИИ владельца KAIF, с подписью агента-автора**:
авторизация не подразумевается, а цитируется — issue #15, слово владельца «Это КАНОН»; доставка
ИСПОЛЬЗУЕТ уже принятое человеком решение, ничего не обходя; транспорт и авторство — две разные
оси; если пермишен-слой агентской системы спрашивает подтверждение исходящего вызова — дай ему
спросить и дождись: подтверждение и стоячая авторизация складываются, а не конфликтуют (полевой
отчёт project A 2.3: прежняя императивная формула читалась классификатором как «публикуй в интернет
не спрашивая» и была отвергнута — дело было в формуле, не в сути правила); send-гейт
`/owner-reviews` остаётся для чужих репозиториев и заявлений от имени владельца; anonymous —
только локально, к origin не тянуться). Канон ветки и шаблоны A/B дословно — payload `framework/skills/report-bug/SKILL.md`
(первоисточник форм — `researches/18` §8; локальную починку ведёт контур «дефект в САМОМ KAIF»
из `AGENT_GUIDE.md`).

**Здесь — исток KAIF:** дефект самого фреймворка И ЕСТЬ дефект этого проекта, отдельная
директория `bugs/KAIF/` не заводится — заводи обычный документ в `bugs/` (заметка в
`bugs/README.md`). Из ветки в истоке живут дедуп перед заведением (`grep -ri "<surface>" bugs/`)
и, для классовых дефектов поставки, fingerprint-строка `kaif-fp:` в теле дока; сигналы парка
(issues origin, отчёты `reports/KAIF_UPDATES/`) — входной поток беклога, см. `reports/README.md`.

## Что делать

1. **Определи следующий номер.** `ls bugs/` → максимальный двузначный `NN` + 1. Имя файла:
   `bugs/NN_<short_english_name>.md` (snake_case, как у соседей; БЕЗ тега `DONE` — баг открыт).

2. **Собери факты ПЕРЕД написанием** (не выдумывай — документ бага ценен своими фактами):
   - Симптом: что именно наблюдается (и чем это отличается от ожидаемого).
   - Воспроизведение: детерминированные шаги. По возможности — через стенд, чтобы баг воспроизводился без человека.
   - Форензика: логи / файл краша / измерения — приложи ключевые строки (стек, сообщение abort, коды
     ошибок, размеры).
   - Сборка/версия, окружение, режим.

3. **Напиши документ по канону** (структура как у существующих документов по багам):
   ```
   # Bug NN — <однострочное описание>

   **Status:** 🔴 OPEN   (или 🟡 partial / 🔬 research-only / 🔧 fix pending verification)
   **Version/build:** <build>   ·   **When/context:** <дата, во время какой задачи найдено>
   **Severity:** S1 | S2 | S3   <сверяется В МОМЕНТ ЗАВЕДЕНИЯ — лестница тяжести, BUG_FIXING_FRAMEWORK.md;
   S3 получает ОДНУ строку в EXPERIENCE.md вместо этого документа>
   **Fix accepted when (observable):** <что будет ВИДНО работающим после фикса — пишется по
   REQUIREMENTS_FRAMEWORK.md; уточняется по мере расследования — или четырёхстрочным сценарием:
   Ситуация · Действие · Результат · Проверка («Сценарная форма»)>

   ## Symptom
   <что наблюдается>

   ## Repro (deterministic)
   <шаги; команды стенда, если есть>

   ## Forensics
   <ключевые логи / краш / измерения>

   ## Root cause / Hypotheses
   <причина, если ясна; иначе ранжированные гипотезы — НЕ патчи вслепую>

   ## Fix plan (or the fix, if done)
   <шаги; связь с архитектурой / другими багами>

   ## Decisions made without the owner
   <заполняется при закрытии: каждое решение, принятое агентом в одиночку (и как выбирал), или "none">

   ## Links
   <связанные баги / идеи / интервью>
   ```
   Следуй `BUG_FIXING_FRAMEWORK.md`. Если баг в сторонней библиотеке, заведи тикет им (например,
   через `gh`) и сошлись на него из документа.

4. **Зафиксируй в беклоге/процессе:**
   - Если важный/блокирующий — короткая строка в `STATUS.md`.
   - Закоммить (в автоциклах — по обычной дисциплине): `node tools/commit.mjs "docs(bugNN): …"`.

5. **Жизненный цикл:** пока открыт — заводи БЕЗ `DONE`. Когда ПОДТВЕРЖДЁННО закрыт (исправлен и проверен) — переименуй
   `git mv bugs/NN_x.md bugs/NN_DONE_x.md` и допиши раздел `## ✅ STATUS: DONE (дата + время)` (что
   сделано / как проверено). Ревизия беклога — навык `/check-backlog`.

## Заметки
- Лучше завести баг и оставить его открытым, чем потерять. Фактическая точность важнее красивого текста.
- Если баг сопротивляется (≥3 слепых попыток исправления) — переключись на `/bug-research` (исследование без кода) по тому же документу.
