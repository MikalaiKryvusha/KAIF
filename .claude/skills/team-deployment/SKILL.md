# /team-deployment — развернуть команду ИИ-агентов

Одного агента дисциплинирует канон KAIF; КОМАНДЕ агентов нужна ОРГАНИЗАЦИЯ — явные роли, схема
адресации, регламент общения, статус-доска, git-дисциплина и правила общей машины. Этот навык
превращает собранную руками полевую практику в повторяемое развёртывание: анализирует проект,
предлагает дизайн команды и материализует его.

Направляющий принцип (он же первое правило размера):

> **Оптимизируй организацию когнитивной работы, а не число агентов.**
> Не порождай агентов потому, что можешь. Порождай потому, что этого требует граф работы.

С навыком едут пять референсов в `references/` — четыре шаблона, которые копируют и адаптируют
(никогда не восстанавливай по памяти), и adopt-путь для уже работающей команды:

| Референс | Становится (предлагаемое имя) |
|---|---|
| `references/team-constitution-template.md` | `TEAM_CONSTITUTION.md` — рабочий канон команды |
| `references/team-status-board-template.md` | `TEAM_STATUS.md` — живая статус-доска (вне git) |
| `references/team-roles-library.md` | контракты ролей в конституцию + инструктажи ролей |
| `references/team-ci-template.md` | `.github/workflows/team-ci.yml` — CI, который едет с командой |
| `references/team-adopt.md` | файла нет — adopt-путь: инвентарь · трёхведёрная дельта · решение владельца |

**Границы навыка (намеренные).** Он поставляет МЕТОДОЛОГИЮ в markdown: конституцию, доску,
ролевые контракты, архетипы, процедуры. Он НЕ поставляет оркестратор: ни машинерии-планировщика,
ни YAML-схем, ни автоматики метрик, ни автореконфигурации — команде дисциплинированных
KAIF-агентов с ролью менеджера ничего из этого не нужно, чтобы начать, и полевая команда это
доказала. Инструменты, которых требует конституция (правка доски, рабочие места), строит АГЕНТ
ПРОЕКТА по контрактам из шаблонов — то же правило, что у контура вычитки: KAIF фиксирует, что
обязано быть; проект строит, как.

**Командный режим ДОПОЛНЯЕТ канон, никогда не заменяет.** Каждая роль работает по полному
фреймворку KAIF проекта в рамках своей специализации и своей зоны ответственности. Конституция
связывает ПОВЕРХ `AGENT_GUIDE.md`, а не вместо него.

## Операция 1 — analyze: профиль проекта до предложения кого бы то ни было

Никогда не начинай с «сколько агентов хотите». Начинай с работы.

1. Прочитай канон проекта (`STATUS.md`, `MASTER_PLAN.md`, карты) и назови **профиль проекта**
   категориями, не числами: тип · домен · зрелость · размер · сложность · риск · сложность UI ·
   трудность верификации · потенциал параллелизма · плотность зависимостей · длительность.
2. Назови **требуемые способности** — виды экспертизы, которые работе реально нужны (продуктовое
   мышление, архитектура, дизайн UI, реализация, верификация, релиз…), каждую с пометками:
   обязательная или опциональная · уровень риска · примерный объём · требует ли НЕЗАВИСИМОСТИ
   (судья не судит собственную работу).
3. Назови **ограничения машины и владельца**: сколько параллельных сессий держат железо и
   внимание владельца; какие ресурсы — синглтоны (стенд, эмуляторы, порты, дверь выката);
   сколько человеческого времени есть на одобрения.

Выход: короткая аналитическая записка (план или разведдок по конвенции проекта). Команды ещё нет.

## Операция 2 — suggest: обоснованный дизайн команды, одобренный владельцем

0. **Команда УЖЕ работает здесь → adopt-путь (`references/team-adopt.md`), а не дизайн.**
   Инвентаризуй живую конституцию, доску, инструменты и имена против канона → разложи каждую
   дельту в *matches* · *bring-to-canon* · *better-than-canon* (СИГНАЛ В ORIGIN, не дефект) →
   владелец решает ДО любого изменения → применяй только одобренное, не трогая записанных слов
   владельца; два слова владельца на один параметр → побеждает слово владельца проекта, как
   `FORK:`. Операция 3 затем применяет ТОЛЬКО одобренные bring-to-canon пункты — никогда не
   копируй поверх живой конституции.
1. Возьми ближайший **архетип** из `references/team-roles-library.md` (web-product-small ·
   web-product-medium · hardware-lab-small — последний всякий раз, когда один физический синглтон
   под тестом сериализует основную работу) и адаптируй: опциональные роли активируются только по
   условию (архитектор — сложность архитектуры от средней; дизайнер — сложность UI от средней;
   второй/третий инженер — параллелизуемая работа превышает устойчивый темп одного).
2. Размер — по стартовым эвристикам, затем оправдай каждое место:
   - низкая сложность → 1–2 агента · средняя → 3–6 · высокая → 5–9, поэтапно;
   - каждый добавленный агент оплачивается НЕЗАВИСИМОЙ работой, которая существует без выдумки;
   - координация — это цена: место, дающее больше синхронизации, чем параллельной работы, — режь.
3. Прогони дизайн по **антипаттернам** (ниже). Совпавшее — убей.
4. Вынеси дизайн владельцу как решение — состав, кто кому отчитывается, что кому принадлежит,
   что остаётся владельцу — через канал вопросов проекта (интервью или контур вычитки).
   **Состав команды — решение уровня владельца**: оно тратит его машину, деньги и внимание.
   До его «да» не разворачивай ничего.

## Операция 3 — deploy: материализовать одобренный дизайн

1. **Конституция.** Скопируй `references/team-constitution-template.md` → `TEAM_CONSTITUTION.md`;
   заполни плейсхолдеры (имя команды, карта ролей, ресурсы проекта, замки-синглтоны); вставь
   контракты взятых ролей из библиотеки; удали роли, которых дизайн не взял. Девять
   секций-инвариантов остаются — это оплаченные полевые уроки, не украшение.
2. **Статус-доска.** Скопируй `references/team-status-board-template.md` → `TEAM_STATUS.md`
   (строка на роль) **и тем же движением внеси её в `.gitignore`** — доска есть состояние
   сессии, а не история (шаблон → «Где живёт доска»; именованный опт-аут — за владельцем).
   Построй или адаптируй инструмент доски по контракту из шаблона: одна доска на команду,
   достижимая из каждого рабочего места; каждая роль переписывает ТОЛЬКО свою строку; запись
   атомарна; `audit-waiting` бьёт тревогу.
3. **Рабочие места.** По изолированному месту на каждую исполняющую роль; менеджер — в главной
   копии. Для git-проектов референс-механизм — `git worktree` с инвариантом именования
   **адрес сессии = имя каталога = имя ветки = `<проект>-team-<роль>`** (образец — слово
   владельца: `проект-team-роль`): приписка проекта отличает окна команды от чужих проектов
   той же машины, вставка `team` с одного взгляда помечает каталог как командное место, суффикс
   называет роль. Инструмент рабочих мест строится по контракту из шаблона конституции
   (create / list / reset-от-main / remove).
4. **Инструктажи ролей.** Для каждого места подготовь инструктаж менеджера из контракта роли:
   ты — <Роль> · твоя зона · прочитай конституцию целиком · выполни ритуал возобновления проекта
   на СВЕЖЕМ main · объяви себя на доске · доложи о готовности.
5. **Запуск.** Владелец открывает по окну на роль и набирает по одной строке в каждом
   (переименование сессии в адрес роли). Всё остальное — работа менеджера: свежий `main` каждой
   роли ДО её ритуала возобновления, затем инструктажи, затем раздача задач — **при первом
   запуске**, когда бы владелец ни открыл окна; до того честно докладывай «жду окон».
6. **CI едет с командой** (приказ владельца, issue #29 истока). Материализуй
   `.github/workflows/team-ci.yml` из `references/team-ci-template.md` — fenced-блок плюс его
   пять констрейнтов (только дешёвые гейты, команды ЧИТАЮТСЯ из `package.json` / канона сборки,
   красный CI блокирует мерж по § 5 конституции, не-GitHub remote получает тот же job именованным
   pre-push скриптом). Как и каждый артефакт этой операции — по «да» владельца.

## Операция 4 — status: доска — общая правда команды

Менеджер читает доску перед раздачей и следит за здоровьем команды: трение, простой ролей,
узкие места, неравномерная загрузка контекста. Каждая роль обновляет свою строку при каждой
смене состояния (взял задачу · жду · освободился). Доска показывает момент; эстафету между
сессиями по-прежнему несёт `STATUS.md` проекта — доска его никогда не заменяет.

## Операция 5 — retrospective: после вехи суди ОРГАНИЗАЦИЮ

Триггеры: веха — **и дремота**: окна закрыты, соло-сессии продолжаются, а ролевые ветки лежат
несмерженными — это тихий организационный долг, и он открывает ретроспективу ровно так же, как
веха. Доска в том виде, в каком стояла на конец смены, копируется в документ ретроспективы (сама
доска в git не живёт — шаблон → «Где живёт доска»).
Ответь письменно: верно ли укомплектована команда · какие роли перегружены / недогружены ·
каких способностей не хватило, какие дублировались · где координация стала узким местом · какие
гейты верификации ловили настоящие дефекты · что менять в следующем развёртывании. Предлагаемые
изменения — явные, не общие наблюдения. Реконфигурация (добавить/убрать/слить места) — это
редизайн: заново прогони suggest на свидетельствах и возьми «да» владельца. Уроки — в журнал
опыта проекта: следующая команда стартует умнее.

## Антипаттерны — распознавай и отказывай

- **Взрыв агентов** — агентов больше, чем независимой работы.
- **Бутылочное горлышко менеджера** — вся работа ждёт одного перегруженного координатора.
- **Коллапс верификации** — нет независимого судьи при повышенном риске.
- **Дублирование ролей** — два места делают одно и то же рассуждение.
- **Мутация общего рабочего места** — двое пишут в один каталог.
- **Двусмысленность полномочий** — две роли считают решение своим.
- **Безграничная коллаборация** — постоянный плотный трёп многих ролей.
- **Бюрократическое переусложнение** — организация сложнее проекта.

## Оплаченные полевые уроки (почему шаблоны говорят то, что говорят)

Они стоили живой команде реальных инцидентов; едут в шаблоне конституции и есть причина, почему
этот навык — дистилляция, а не теория:

1. **Свежий `main` ДО ритуала возобновления — и это обязанность МЕНЕДЖЕРА.** Роль, освежившая
   контекст на отставшей ветке, докладывает устаревшие числа с полной уверенностью: она честно
   прочитала то, что у неё лежало.
2. **Номера документов присваивает менеджер при мерже.** Ветки ролей не видят друг друга;
   «следующий свободный номер» сталкивается. Роли заводят плейсхолдеры `NEW_<слаг>`.
3. **Недоставленное сообщение НЕ пересылается постороннему.** На машине живут сессии чужих
   проектов. Результат уже в артефактах (ветка, строка доски) — пометь «отчёт не доставлен» и
   завершай.
4. **Контекстные окна — ресурс, который балансирует менеджер.** Крупная работа режется на
   порции в одну сессию; тяжёлое чередуется между местами; роль, чувствующая тяжесть контекста,
   говорит об этом одной строкой — это сигнал ресурса, а не слабость.
5. **Статус-доска живёт в ОДНОМ месте**, достижимом из каждого рабочего места, — иначе у каждой
   роли своя доска, которую никто не читает.
6. **Ресурсы-синглтоны берутся под замок на доске** (стенд, эмуляторы, порты): взял → прогнал →
   отдал; держать «на всякий случай» запрещено.
7. **Мержи — только через менеджера и только после вердикта судьи.** Push роли может быть
   заперт — тогда менеджер ревьюит и пушит; это две разные двери, обе остаются.

## Готово, когда

- Владелец одобрил дизайн команды (состав, линии отчётности, владение).
- `TEAM_CONSTITUTION.md` и `TEAM_STATUS.md` существуют, заполнены из шаблонов.
- Инструменты доски и рабочих мест существуют по своим контрактам и доказаны на сломанном
  случае (правка чужой строки отвергнута; брошенный замок снят).
- У каждого места — рабочее место, инструктаж и старт со свежего `main`; `team-ci.yml`
  существует (или именованный pre-push скрипт для не-GitHub remote), а доска игнорируется git.
- При первом запуске прошёл первый круг раздачи: задачи поставлены формой сообщения из
  конституции, отчёты вернулись формой отчёта (до открытия окон — «жду окон»).
- Живая команда ПРИНЯТА, а не перезаписана: решение владельца по дельте записано, а формулировки
  локальной конституции пережили побайтно всё, кроме одобренных добавлений.
