## Symptom

`❌ S2 update → 9.9 exit 0 — update: checking …/src-9.9\nupdate: 2.4 → 9.9` — вывод команды
обрывается сразу после строки версии; следующая ожидаемая строка (`⟳ synthetic baseline: …` или
`+ pre-update backup`) не напечатана; `KAIF_UPDATE_TASK.md` не создан, `.kaif/backup-*` и
`update-journal.json` не появились → смерть ДО `backupTree`, в окне
`stableValues → buildSyntheticBaseline (fetchMaybe: сетевой fetch ${ORIGIN}/releases/download/v2.4/…,
таймаут 30 с) → loadRehearsal`. Повторный запуск той же команды в оставленном корне — зелёный
(лог `rerun.log` рядом с корнем `kaif-sbx-l4-noise-FH5kPp`).

Вхождения: 2026-09-04 сессия 50 — s07 T1, затем T2 (2 из ~12 прогонов); сессия 51 — s10 S2
(1 из 3 прогонов дня). Отдельные прогоны s07 ×5 и повтор s10 — зелёные.

## Repro (deterministic)

НЕ воспроизводится детерминированно (флейк). Воспроизводимая половина — форензика: см. «Fix
accepted when» (селфтест раннера).

## Forensics

- s10 (сессия 51): `e.status ?? 1` = 1 напечатан как `exit 0`-ассерт с хвостом двух строк stdout;
  stderr отсутствует в выводе (`2>&1` стоит — значит, процесс НЕ печатал в stderr, либо был убит
  сигналом: `e.status` undefined → `?? 1`). Свод затем упал сам (`readFileSync` несуществующего
  задания) — форензики не оставил (`run()` s10 не писал `run-fail`).
- s07 (сессия 50): тот же хвост; форензика поставлена ТОЛЬКО в s07 (`run-fail-N.log`), с тех пор
  s07 зелёный.
- Общее у трёх вхождений: обрыв ПОСЛЕ `update: X → Y` и ДО первой записи на диск; окно содержит
  единственный сетевой вызов прогона (`fetchMaybe` → GitHub release asset v2.4) и `AbortSignal.timeout`.

## Root cause / Hypotheses

Ранжированы; ни одна не подтверждена — улик нет по вине сводов (класс закрыт ниже).

1. **H1 (лошадь) — процесс убит без stderr в окне сетевого fetch:** `fetchMaybe` ловит исключения
   и возвращает `null`, но смерть без вывода ≠ исключение — это abort/сигнал. Кандидаты: libuv
   assertion на win32 при живых undici-хэндлах (EXP-0085 — класс уже ловился на `process.exit`
   ПОСЛЕ fetch; здесь — ДО завершения fetch) при параллельной нагрузке (сегодня рядом шли Chromium
   `readme-pdf` и второй прогон полигона/контур). Проверка: следующий `run-fail-N.log` покажет
   `signal`/`Assertion failed`.
2. **H2 — сеть: GitHub отдал не-2xx/обрыв на `releases/download/v2.4`** — но тогда `fetchMaybe`
   вернул бы `null` и `update` продолжил бы классическим путём с печатью строки, а не умер молча.
   Против H2: тишина. Проверка: тот же лог (строки после версии).
3. **H3 — Windows-антивирус/индексатор держит свежий файл в temp** → EBUSY/EPERM → исключение со
   стеком в stderr; против: стека нет.
4. **H4 (дописано сессией 55, 2026-09-05, эпик UR) — окно сетевого fetch в `update` шире, чем кажется:**
   после строки версии `update` идёт в сеть ДВАЖДЫ — за парой машинерии (`--source`, у полигона
   локальный) и за артефактом ПРЕДЫДУЩЕГО релиза для синтетического baseline
   (`buildSyntheticBaseline(cur)` → `github.com/…/releases/download/v<cur>/…`, если не задан
   `--baseline`). Своды s09/s10/s18 не передают `--baseline` — каждый их `update` ходит в GitHub за
   ~1 МБ бандла v2.5, и именно этот вызов живёт в окне «после строки версии». Не подтверждено (улик
   по-прежнему нет), но это первое место, где полигон ЗАВИСИТ от сети. Дешёвая митигация — у нового
   свода `s21` каждый `update`/bootstrap получает `--baseline <локальный каталог>` (сети нет);
   перевод s09/s10/s18 на тот же приём — кандидат при следующем вхождении флейка.

Фикс-кандидат для класса «полигон ходит в сеть» (после форензики): `--baseline <локальная копия
v2.4>` в сводах, чтобы полигон не зависел от GitHub, — решение после первого лога.

## Fix plan (or the fix, if done)

1. ✅ `tools/lib/sandbox-run.mjs`: `coreRunner(ROOT, { maxBuffer })` — общий раннер команд ядра с
   форензикой упавшего вызова (`run-fail-N.log`: команда · cwd · status/signal/code/message · полный
   вывод), `--selftest` доказывает оба ответа (файл на красном, отсутствие на зелёном, вывод
   зелёного побайтно равен прямому вызову).
2. ✅ Все своды с раннером формы `execSync(node <cwd>/.kaif/kaif-core.mjs …)` переведены на
   `coreRunner(ROOT)` (s07 — на общий, его локальный дублировал бы класс); своды с раннерами
   инструментов (`.kaif/tools/*`) — на `failed(e, ctx)` из того же помощника.
3. ⏳ Следующее вхождение флейка → `run-fail-N.log` из любого свода → гипотеза подтверждается или
   опровергается наблюдением; тогда фикс причины (или `--baseline` для полигона) и DONE.

`DURABLE-AT:` момент возврата из `execSync` с ошибкой — файл пишется ДО того, как свод решит, что делать дальше (падение самого свода на следующей строке улику уже не теряет)
