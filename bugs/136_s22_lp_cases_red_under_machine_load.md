# Bug 136 — Свод `s22 D` (LP3 и забор из IndexedDB) краснеет в полном полигоне на загруженной машине, в одиночку зелёный

**Status:** 🔧 fix pending verification 2026-11-07 14:42 +03:00 — ожидания свода `s22` по состоянию (часть 5 · готовность сторожа `--wait` · пять близнецов); под
стендом нагрузки HEAD красен (2), правка — 0 в четырёх прогонах; полигон 1 из 3 (14:27–14:38) зелёный; отчёт `testcases/reports/2026-11-07_bug136-s22-waits-under-load.md`.
Прежде: 🔴 OPEN — заведён 2026-11-07 13:56 +03:00 (сессия 99) после двух красных за день на разных случаях одной части свода.
**Severity:** S2 — потерян прогон (два полных полигона ≈ 25 минут); вещь (контур поставки) не сломана — наблюдение ниже.
**Version/build:** исток, сборки 822–826 (`e9ee8f7` … `23a2dd0` + правка HC2) · **When/context:** 2026-11-07, гейты коммитов HC4 и HC2.
**Fixing:** эта сессия — после коммита HC2 (`plans/140`), до судьи эпика HC.
**Fix accepted when (observable):**
- Ситуация. Машина под нагрузкой: соседняя сессия держит игру, CPU ≈ 87 % без полигона.
- Действие. Агент гоняет `npm run test:core` три раза подряд.
- Результат. Часть D свода `s22` зелёная во всех трёх прогонах; ожидания свода ждут состояния, а не секунды.
- Проверка. `grep -c "^❌ s22 D" <лог>` = 0 в трёх логах полигона подряд при загрузке CPU ≥ 80 % (замер — строка «CPU load %» пробы стенда в отчёте).

## Symptom

Полный полигон: 12:20:17 → 12:31:36 — `❌ s22 D: «Записать» при мёртвом сервере → «сохранён на этом компьютере» … — Записываю…|Сервер контура
недоступен…`; 13:37:28 → 13:52:09 — пять ❌ подряд начиная с `s22 D: после ЖЁСТКОГО убийства браузера --queue --list забрал ответ безоконно
ИЗ IndexedDB` (запись `{}`, документ не вписан, замок не снят). Тот же свод в одиночку — зелёный: 12:31:53 → 12:33:55 и 13:53:23 → 13:55:32.

## Repro (deterministic)

Не детерминирован. Условие обоих красных: полный полигон, машина под нагрузкой — стенд в 13:52: «CPU load %: 87» без полигона, за 3 с процесс
`ConanSandbox-Win64-Shipping` набрал ≈ 23,8 с процессорного времени (≈ 8 ядер), полигон шёл ≈ 14,5 мин вместо ≈ 10.

## Forensics

`tools/sandbox/s22-contour-shipped.mjs` раздел (5) — ожидания по часам, не по состоянию: `gen2.child.kill(); await wait(1000)` (сервер «мёртв»
через секунду); статус после клика «Записать» читается таймером внутри страницы; `page.close(); await wait(2000)` перед `--queue --list` (жёсткое
убийство браузера — запись должна успеть лечь в IndexedDB, а профиль — освободиться). Красный второго прогона — «recovery deferred» не наступил
или IndexedDB пуста: оба — времена, которые под нагрузкой длиннее.

## Root cause / Hypotheses

1. (ведущая) Фиксированные ожидания свода короче, чем браузер и сервер успевают под нагрузкой ≈ 8 ядер чужим процессом. Проверка: замер
   длительности каждого шага раздела (5) в одиночку и в полигоне под нагрузкой; ожидания заменить опросом состояния с потолком.
2. Параллельный свод полигона держит тот же профиль браузера (проверить: в полигоне своды идут последовательно — тогда исключено).

## Fix plan

Заменить фиксированные `wait(…)` раздела (5) опросом того, чего ждут: процесс сервера завершён · статус страницы сменился с «Записываю…» ·
процесс браузера завершён и профиль свободен — с потолком и строкой «ждал N мс» в выводе; три полигона подряд под нагрузкой.
