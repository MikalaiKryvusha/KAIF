## Вектор цели (Avoid)

Не допустить необратимой молчаливой потери когнитивной поставки интервала (нормы, policy-changes,
диффы конфликтных модулей) при том, что маркер, расписка и history уже переведены на новую версию,
а `update-verify` зеленеет по чек-листу ЧУЖОГО интервала. Для анонимных и pre-1.5 развёртываний
bootstrap — ЕДИНСТВЕННАЯ дорога обновления, поэтому дыра бьёт именно по тем, у кого запасной нет.

**Fix accepted when (observable):** после шага «bootstrap 2.3» выполняется ОДНО из двух — либо
`head -1 KAIF_UPDATE_TASK.md` печатает «finish the update to 2.3» И `grep -rl UPSTREAM-NEWS-2.3 .
--exclude-dir=.git` находит файл (задачу или `*.superseded.md`), либо команда завершается ненулевым
кодом и НЕ трогает `.kaif/kaif.json` и `.kaif/last-update.json`.

**Сегодняшнее измеренное состояние:** задача говорит 2.2, grep не находит ничего, маркер уже 2.3 —
оба исхода сегодня ложны, критерий различает починку от текущего поведения.

## Symptom

`framework/installer/KAIF-CORE.mjs:1786` — ветка срабатывает по НАЛИЧИЮ чек-поинтов, а не по
интервалу версий:

```js
    if (existsSync(UPDATE_TASK) && /^KAIF-UPDATE: /m.test(readFileSync(UPDATE_TASK, 'utf8'))) {
```

Наблюдение: `= kept existing KAIF_UPDATE_TASK.md (it carries recorded checkpoints — not overwritten)`
при том, что интервал СМЕНИЛСЯ.

## Repro (deterministic)

Пять шагов, полностью — в карточке F3 аудит-отчёта: install 2.1 → правка модуля владельцем →
bootstrap 2.2 → `checkpoint review-news` → обрыв сессии → bootstrap 2.3.

## Root cause

Гарантия — свойство пути, а не дерева (семейство 4). fail-closed поверх незакрытой задачи
(`bugs/25`) живёт на дороге core-update; bootstrap с тем же деревом её не имеет. Соседние
комментарии закрывают два СМЕЖНЫХ случая (re-run той же версии — `bugs/14`; задание прошлого
интервала БЕЗ чек-поинтов — `bugs/25`), а их пересечение не покрыто ничем.

## Фикс (как сделано)

Одно условие: ветка отвечает на вопрос «тот же ли ИНТЕРВАЛ?», а не «есть ли чек-поинты?».

```js
    if (legacyOld.version === meta.version
        && existsSync(UPDATE_TASK) && /^KAIF-UPDATE: /m.test(readFileSync(UPDATE_TASK, 'utf8'))) {
```

Задача с чек-поинтами из СТАРОГО интервала теперь падает в ту же ветку, что и задача без них
(строки 1828–1835): сохраняется как `KAIF_UPDATE_TASK.superseded.md` и заменяется задачей нового
интервала. Строка лога называет РОД сохранённого («WITH recorded checkpoints») — сессия, читающая
голое «unfinished», переделала бы уже записанные пункты. Отдельно: если superseded-копия УЖЕ
существовала и её не разобрали, лог говорит об этом вслух, а не затирает молча.

## Decisions made without the owner

1. **Вариант 1 (перегенерация), а не вариант 2 (fail-closed).** Оба стоили одинаково, но
   fail-closed отказывает — а для анонимных и pre-1.5 развёртываний bootstrap единственная дорога
   обновления, и отказ оставил бы их вообще без хода. Вариант 1 при этом строго сильнее: он и
   доставляет новый интервал, и сохраняет прежнюю поставку в superseded-копии.
2. **Строка лога различает род сохранённого.** Прежний текст «an unfinished … was preserved»
   верен и для задачи с чек-поинтами, но неполон: записанные пункты — чужая сделанная работа, и
   сессия, не знающая о них, переделает их. Добавлено «WITH recorded checkpoints» и «and for the
   items it already records».
3. **Повторное затирание superseded-копии оставлено, но озвучено.** Два неотработанных интервала
   подряд по-прежнему оставляют один файл (побеждает свежий). Уникализация имени потребовала бы
   новой строки в ignore-first, а значит правки `.gitignore` в каждом полевом проекте — цена
   несоразмерна риску второго порядка. Молчания больше нет: лог называет замену и говорит, что
   прежнюю копию можно достать из git.
4. **Критерий приёмки карточки уточнён замером.** Дословный `grep -rl UPSTREAM-NEWS-<ver> .
   --exclude-dir=.git` зеленел БЫ и на сломанном коде: бандл-источник `.kaif/install/
   KAIF-CORE-BUNDLE.md` несёт ту же строку по построению (замерено ДО правки — см. ниже). Свод
   якорит примету на САМУ ЗАДАЧУ, а не на дерево.

## TWINS

`TWINS: searched` — ветки bootstrap, решающие судьбу задания по НАЛИЧИЮ содержимого вместо
интервала версий. Найдено 1 других места: ветка `TASK_FILE` (1842–1852, адаптационное задание) —
она проверяет `/^KAIF-ADAPT: /` тоже без интервала, **но это НЕ близнец**: механизм провала другой.
Адаптационная задача не привязана к интервалу версий вообще (адаптация бывает один раз, на свежей
установке), и ветка не «сохраняет вместо перегенерации» — она БЕЗУСЛОВНО уносит задание в
`KAIF_ADAPTATION_TASK.superseded.md` и удаляет оригинал, то есть уже ведёт себя так, как должна
была вести себя починенная ветка обновления. Назвать поломку у неё нечем — опровергнут (EXP-0051).
