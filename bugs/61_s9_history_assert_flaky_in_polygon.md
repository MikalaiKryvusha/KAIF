## Symptom

`tools/sandbox/s03-receipts-tools.mjs`, профиль S9:

```
❌ S9 история растёт: 2 записи после второго update
```

Ассерт проверяет `mk.history.length === 2 && mk.history[1].from === '9.9' && to === '9.10'` после
ВТОРОГО `update --source <9.10>`. Значит второй `update` не дошёл до `appendHistory`.

## Forensics

Улика второго `update` в момент падения **не была захвачена**: ассерт вызывался без поля `extra`,
и вывод команды выброшен. Это ровно вторая половина `EXP-0052` («хвост показывает итог, а нужна
причина»), только на уровне самого ассерта, а не `| tail`.

**Сделано в эту сессию:** ассерт теперь несёт `code=${r.code} · ${r.out.slice(-500)}` — следующее
падение назовёт и код возврата второго `update`, и его последние строки. Ассерт НЕ ослаблен:
условие прежнее, добавлена только улика.

## Root cause / гипотезы (ранжированы)

1. **Отказ второго `update` по неубранному заданию.** Свод сносит `KAIF_UPDATE_TASK.md` через
   `rmSync(..., { force: true })` прямо перед вторым `update`, а `cmdUpdate` fail-closed по
   `okOnDisk(UPDATE_TASK)` (bugs/25). Если удаление на Windows иногда не успевает стать видимым
   следующему процессу, `update` откажет с кодом 1 → история останется одной записью. Проверяется
   захваченной уликой: ждём строку `KAIF_UPDATE_TASK.md exists — the previous update was never
   verified`.
2. **Транзиентный отказ файловых операций Windows** внутри `classifyAndApply`/`backupTree`
   (EBUSY/EPERM от антивируса или индексатора на свежесозданном дереве) — тогда в улике будет
   стектрейс с кодом ошибки.
3. **Разделяемый ресурс уровня OS-temp.** Наименее вероятна: корни прогонов уникальны по
   построению с `bugs/59` (`tools/lib/temp-root.mjs`), преполёт это проверяет.

Гипотеза 3 названа, чтобы её не искали заново; работать надо с 1 и 2.
