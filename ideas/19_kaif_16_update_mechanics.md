# Исследование 15 — Отчёт для KAIF: что мешало обновиться с 1.5 на 1.6 в проекте веб-приложения NDim Space

> **Кому.** ИИ-агенту, который разрабатывает KAIF (и владельцу фреймворка).
> **Откуда.** Живое обновление проекта NDim Space с KAIF 1.5 на 1.6 «Homeostatic KAIF»,
> 2026-07-26. Путь: `node .kaif/kaif-core.mjs update` (release-канал) → ревизия дифа → ручная
> сшивка → `check` → судейский проход → `update-verify`. Полный след — коммит этой сессии,
> точка отката — тег `pre-kaif-1.6`.
> **Что это.** Полевой отчёт о **механике обновления**, а не о содержании релиза. Содержание
> 1.6 — отличное: это ровно то, что просил `researches/14`, и почти всё легло в проект
> дословно. Ниже — про то, что стоило дорого при установке.
>
> **Дисклеймер честности.** Всё ниже наблюдено на ОДНОМ обновлении ОДНОГО проекта с двумя
> нетипичными свойствами: (1) рабочий язык — русский, и проект перевёл на русский даже
> агентские документы (расхождение с каноном 1.5/1.6); (2) развёрнуты все пять агентских
> систем. Дефекты F1, F3, F4, F6 от этих свойств не зависят; F2, F5, F7 — усиливаются ими.

## F1 🔴 Снапшот sha в `deploy-manifest.json` протухает: «разошедшийся» превращается в «нетронутый»

**Это главный дефект.** Он ломает основную гарантию бережного обновления, и ломает молча.

**Механизм.** В конце `cmdUpdate` манифест пересобирается так:

```js
const shas = {};
for (const p of [...deployedPaths, ...agentPaths]) if (okOnDisk(p)) shas[p] = fileSha(p);
```

Снимается sha **того, что лежит на диске**, — независимо от того, был файл заменён или
классифицирован как `diverged` и СОХРАНЁН. То есть после обновления запись в манифесте для
сохранённого файла означает «версия пользователя», а классификатор следующего обновления
читает её как «наш шаблон, никто не трогал»:

```js
if (oldShas[f.path] && fileSha(f.path) === oldShas[f.path]) {
  writeFileSync(f.path, content);   // «нетронутый» → молча заменяем
} else { diverged.push(f.path); }
```

**Что это дало в бою.** В обновлении 1.4→1.5 (2026-07-17) агент восстановил русский
`BUG_FIXING_FRAMEWORK.md` — он попал в манифест как «нетронутый». В обновлении 1.5→1.6
механика заменила его английским шаблоном **без единого слова в отчёте** (в логе — обычная
строка `↻ replaced`). Проверено наблюдением: с результатом механического прохода валидатор
проекта падает:

```
✖ ОШИБОК: 1
  ✖ BUG_FIXING_FRAMEWORK.md: не локализован (нет кириллицы) — рабочий язык проекта русский
```

То же произошло со скиллами `autoloop`, `dayloop`, `nightloop`, `release` (4620 / 5399 / 4197 /
3058 символов кириллицы — стёрты подчистую).

**Почему это класс, а не частный случай.** Инвариант «sha совпал ⇒ пользователь не трогал»
верен ровно один раз — сразу после установки. Начиная со второго обновления он означает
«не менялось с прошлого обновления», а для сохранённых файлов это ровно противоположное.
Любая адаптация, пережившая одно обновление, гарантированно погибает на следующем.

**Предлагаемое исправление.** Хранить в манифесте sha **шаблона, который был развёрнут**, а не
файла с диска:

```js
// вместо fileSha(p) для всех — sha того, что мы РЕАЛЬНО записали
shas[f.path] = sha256(content);   // content = шаблон после подстановки плейсхолдеров
```

Тогда `diverged` = «диск ≠ наш шаблон», и это устойчиво через любое число обновлений. Для
сохранённых файлов запись просто переносится из старого манифеста без изменений.
Побочная выгода — F2 закрывается бесплатно (см. ниже).

## F2 🟠 `KAIF_UPDATE_TASK.md` перечисляет разошедшиеся файлы, но не говорит, в каких из них есть что вливать

Задание выдало список из 22 файлов с формулировкой «содержат локальные правки, влей новинки
шаблона руками». Фреймворк между 1.5 и 1.6 изменил из них **7**. Остальные 15 (`ideas/README.md`,
`bugs/README.md`, `.claude/skills/pause`, `kaif-fork`, `kaif-remove`, `resume`, `revision`,
`what-next`, `help-kaif`, `fix-vision`, `kaif-version`, `kaif-switch-origin`, `kaif-update`,
`propose-idea`, `refresh-context`) не требовали **ничего** — их шаблоны байт в байт совпадают
с 1.5.

Узнать это из проекта невозможно: старый бандл `update-verify` удаляет, а в манифесте лежат sha
файлов на диске, а не шаблонов. Пришлось скачать `KAIF-CORE-BUNDLE.md` из релиза v1.5 (`gh release
download v1.5`) и строить матрицу «шаблон 1.5 × шаблон 1.6 × наш файл из `git HEAD`».

Симметричная проблема на другой стороне: из 23 **заменённых** файлов фреймворк реально изменил
тоже 7 — остальные 16 переписаны идентичным содержимым. То есть агент, добросовестно
просматривающий `git diff` после прохода, видит верный размер работы, а агент, читающий лог
`↻ replaced`, — завышенный втрое.

**Предлагаемое исправление.** Помечать каждую строку задания:
`AGENT_GUIDE.md [шаблон ИЗМЕНЁН — вливай]` против `pause/SKILL.md [шаблон не менялся — ничего
не нужно]`. С исправлением F1 это вычисляется одной строкой: `sha256(новый шаблон) !==
manifest.shas[path]`. Для слабой модели разница принципиальная: 7 файлов вдумчивого чтения
вместо 22 — это разница между «сделает» и «пролистает».

## F3 🔴 `templateNotes` в бандле 1.6 описывают релиз 1.5

Дословно из `kaif-bundle-manifest.json` бандла 1.6:

```json
{ "version": "1.6", "released": "2026-07-24",
  "templateNotes": [
    "fable family vendored: /fable-method, /fable-loop, /fable-judge, /fable-domain …",
    "NEW key doc TESTING_FRAMEWORK.md: the 7 testing principles …",
    "Release codename for this version: KAIF 1.5 — Tested KAIF"          ← 1.5
  ] }
```

Сверено с бандлом релиза v1.5: массив `templateNotes` в 1.6 **байт в байт совпадает** с 1.5.
Это не «устаревшая строчка», это поле, которое к релизу не обновляли вовсе.

Эти же строки механика печатает в `KAIF_UPDATE_TASK.md` под заголовком **«What's new in the
templates»**, и чекпоинт `review-news` предписывает: «прочитай новости шаблонов ниже и примени
всё релевантное к файлам, которые механика не смогла тронуть».

**Итог: агент, честно выполняющий чекпоинт `review-news`, не узнаёт о 1.6 ровным счётом
ничего.** Ни разведартефактов, ни правила трёх дверей, ни пометок провенанса, ни правила
одного шага, ни чеклиста выката, ни guardrail-охот. Всё содержание релиза пришлось брать из
GitHub Release notes (`gh release view --repo MikalaiKryvusha/KAIF`), о которых задание не
упоминает.

Это самый дешёвый в исправлении и самый дорогой по последствиям дефект: **`templateNotes` —
это и есть инструкция по слиянию для слабой модели**, единственный канал, по которому она
узнаёт, ЧТО именно вливать в свои разошедшиеся документы.

**Предлагаемое исправление.** (а) Гейт в релизном пайплайне KAIF: собирать бандл нельзя, если
`templateNotes` не упоминают собственный `version` манифеста — та же логика, что «проверь
стража на сломанной версии». (б) Ещё лучше — генерировать `templateNotes` из раздела «✨ What's
new» релизных заметок, они уже написаны и точны. (в) В `KAIF_UPDATE_TASK.md` добавить прямую
ссылку на релиз: `gh release view vX.Y --repo … --json body` — как запасной путь.

## F4 🟠 `.kaif/install/` (425 КБ) кладётся в отслеживаемое дерево и не попадает в `.gitignore`

`cmdUpdate` делает `mkdirSync('.kaif/install')` и записывает туда `KAIF-CORE-BUNDLE.md`
(425 708 байт). Строки в `.gitignore` для него нет:

```
$ git check-ignore -v .kaif/install/KAIF-CORE-BUNDLE.md
NOT IGNORED
```

`update-verify` каталог удаляет — но только если агент до него дошёл. Между `update` и
`update-verify` лежит вся ручная сшивка (в этой сессии — десятки правок и несколько часов), и
любой `git add -A` в этом окне утаскивает 425 КБ мусора в историю. Я поймал это на себе:
проверочный скрипт сделал `git add -A`, и в индексе оказались `.kaif/install/KAIF-CORE-BUNDLE.md`
и `KAIF_UPDATE_TASK.md`.

Ирония в том, что **1.6 сам вводит правило «сначала ignore, потом инструмент»** («секрет,
пойманный гейтом, — успех процедуры; пойманный владельцем — провал фреймворка»). Инсталлятор
это правило нарушает.

**Предлагаемое исправление.** Либо дописывать `.kaif/install/` в `.gitignore` ДО скачивания
(буквально ignore-first), либо качать во временный каталог ОС вне репозитория. Первое лучше:
строка в `.gitignore` полезна и после очистки — обновления повторяются.

## F5 🟠 Зеркала агентских систем расходятся с каноном и живут так релизами

**Наблюдение, из-за которого находка серьёзнее, чем «окно между двумя командами».** В этом
проекте четыре зеркальные системы держали **английские** скиллы с обновления 1.5 (2026-07-17)
до этого обновления (2026-07-26) — девять дней, весь релизный цикл:

```
.claude/skills/resume/SKILL.md    HEAD кириллицы = 1731   ← канон, русский
.roo/commands/resume.md           HEAD кириллицы =   88   ← только RU-алиасы триггеров
.agents/skills/resume/SKILL.md    HEAD кириллицы =   88
.grok/skills/resume/SKILL.md      HEAD кириллицы =   88
.cline/skills/resume/SKILL.md     HEAD кириллицы =   88
```

Причина: в обновлении 1.5 агент восстановил русские скиллы (EXP-0047), но восстановил их
**только в `.claude/skills/`** — канон починил, зеркала нет. Пересинхронизации в 1.5 не
существовало, и расхождение спокойно пережило релиз. При рестарте моей пересборки зеркал
разошедшимися оказались **92 файла из 113**.



`cmdUpdate` раздаёт копии скиллов в `.agents/`, `.grok/`, `.cline/`, `.roo/` через
`deployAgentSystems`, а тот использует `writeIfNew` — «файл есть, оставляю как есть». В логе это
117 строк `= kept existing …`. В результате сразу после `update` `.claude/skills/autoloop`
содержит 1.6, а `.agents/skills/autoloop`, `.grok/…`, `.cline/…`, `.roo/commands/autoloop.md` —
1.5. У проекта с пятью системами это **113 файлов** в состоянии «предыдущий релиз» (26 скиллов ×
4 системы + 3 файла `references/` × 3 системы) — ровно то число, которое `update-verify` потом
и назовёт в своём отчёте о пересинхронизации.

Механика этого: `update` раздаёт копии через `writeIfNew` («файл есть — оставляю»), поэтому
любая правка канона, сделанная руками агента после прохода, в зеркала не попадает никогда.

**Справедливости ради: 1.6 это чинит.** `update-verify` в конце печатает
`↻ re-synced 113 system skill copies from the canon` — механизм есть, он новый в 1.6 и он
работает (именно он окончательно вылечил девятидневное расхождение выше). Но:

1. Он срабатывает в самом конце, после всей ручной сшивки. Всё это время проект живёт с пятью
   разными версиями одних и тех же скиллов, и агент другой системы (Codex, Cline, Roo) прочтёт
   старый канон.
2. Ни лог `update`, ни `KAIF_UPDATE_TASK.md` об этом не предупреждают. Я потратил отдельный шаг
   на ручную пересборку зеркал (92 файла), не зная, что `update-verify` сделает это сам.
3. Если обновление прервётся до `update-verify` — а на большом слиянии это вероятно, — проект
   останется в смешанном состоянии без единого предупреждения.

**Предлагаемое исправление.** (а) Гонять ту же пересинхронизацию и в конце `update` (операция
идемпотентна, стоит миллисекунды), а в задании написать строкой: «зеркала агентских систем
пересобираются автоматически, руками не трогай». (б) Добавить сверку зеркал в
`kaif-core.mjs check` — тогда расхождение вроде девятидневного выше становится видимым сразу,
а не через релиз. Сейчас `check` проверяет только НАЛИЧИЕ 108 агентских артефактов, но не их
совпадение с каноном.

## F6 🟡 Чекпоинты самозаверяемые: `update-verify` проверяет только наличие строки

`node .kaif/kaif-core.mjs checkpoint judge` просто дописывает `KAIF-UPDATE: judge done` в файл
задания, а `cmdUpdateVerify` грепает наличие этой строки:

```js
if (!new RegExp(`^KAIF-UPDATE: ${id} done$`, 'm').test(task)) { … }
```

Я проставил все четыре чекпоинта разом, **до** судейского прохода, — механика не возразила
(судью я потом честно прогнал, но никто этого не потребовал). Для слабой модели, которую 1.6
ровно и адресует, это бесплатный проход через самый важный гейт релиза.

Как минимум один чекпоинт можно сделать машинным даром: `recheck` предписывает выполнить
`node .kaif/kaif-core.mjs check` — пусть команда `checkpoint recheck` сама его и запускает,
а при ненулевом коде отказывается записывать отметку. Для `judge` — требовать в строке
чекпоинта хотя бы вердикт и одну строку доказательства.

## F7 🟡 Расхождение по языку не управляется, и обновление воюет с ним каждый раз

Языковой пакет `ru` покрывает 9 файлов (`GOAL.md`, `KAIF_FRAMEWORK.md`, 6 README директорий и
`skill-triggers.json`) — точно так же в 1.5 и в 1.6. Всё остальное английское по замыслу, и
`AGENT_GUIDE.md` 1.6 это прямо кодифицирует: «агентские документы — английский, документы
владельца — язык владельца».

Этот проект принял другое решение (развёртывание 1.4, владелец читает и агентские документы;
рабочий язык русский). Решение легальное — но фреймворк о нём не знает, и **каждое обновление
пытается его отменить**, а маркера, которым проект мог бы о нём заявить, нет. Один и тот же
урок пришлось записывать дважды: EXP-0047 (обновление 1.5) и EXP-0051 (обновление 1.6).

**Предлагаемое исправление (по возрастанию стоимости).**

1. Дешёвая эвристика, закрывающая оба инцидента без новых полей: **если развёрнутый файл
   содержит письменность рабочего языка, а новый шаблон — нет, не заменять его; отправить в
   `diverged`.** Одно правило — и ни EXP-0047, ни F1-регрессия этого обновления не случились бы.
2. Поле в `.kaif/kaif.json`: `"localize": "all"` (против умолчания `"owner-facing"`) либо явный
   список `"keep": [...]`, который `update` уважает.
3. Полный русский пакет в бандле — дорого и, честно говоря, не нужно: локализацию проект
   переживёт и сам, ему нужно лишь, чтобы её не стирали.

## F8 🟡 Ловушка CRLF на Windows всё ещё жива (повтор из EXP-0047)

Механика пишет строго LF. Восстановление адаптированного файла через git при
`core.autocrlf=true` (умолчание Windows) возвращает CRLF, после чего валидатор перестаёт
видеть YAML-фронтматтер («нет фронтматтера» ×18 в прошлый раз). В этот раз обошёл заранее:
восстанавливал не через `git checkout`, а через `git cat-file -p HEAD:<путь>` с записью LF из
Node.

Дешёвое лекарство на стороне KAIF: класть при развёртывании `.gitattributes` со строкой
`*.md text eol=lf` — тогда ловушка не может повториться ни у кого, независимо от аккуратности
агента.

## Что стоило бы добавить в механику (запросы функциональности)

1. **`update --dry-run`.** Перед проходом я написал скрипт, который сравнивает sha каждого
   файла с манифестом и печатает «будет заменено молча / сохранено / добавлено», с пометкой,
   в каких из заменяемых есть кириллица. Он показал 131 файл под молчаливую замену — и именно
   он превратил обновление из лотереи в работу. **Это должно быть встроенной командой.**
   Ровно по духу 1.6: «зеркало прода снимается ДО того, как его трогать».
2. **Сохранять бандл предыдущей версии** (или его URL) в `.kaif/` после обновления. Без базы
   для трёхстороннего сравнения агент вынужден выбирать между «принять шаблон и потерять
   адаптацию» и «оставить своё и потерять новинки релиза». С базой он делает нормальный
   мёрдж. Стоимость — один файл; выгода — единственный способ сшить честно.
