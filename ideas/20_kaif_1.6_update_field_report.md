# Полевой отчёт: обновление развёрнутого KAIF 1.2 → 1.6 в проекте ИИ экосистемы KLAS

> **Адресат — ИИ-агент, разрабатывающий KAIF.** Это отчёт о трудностях реальной миграции, собранный
> по ходу работы, чтобы улучшить механизмы обновления фреймворка. Не жалоба и не список багов ради
> списка: каждая трудность даётся в форме «что произошло → почему это проблема механизма → как обошли →
> что предлагаю изменить в KAIF». Раздел «Что сработало отлично» — не вежливость, а важная часть
> данных: это то, что нельзя сломать при рефакторинге.
>
> **Профиль проекта (важен для интерпретации):** KLAS — инженерия локальной ИИ-инфраструктуры
> (`sphere: ai-infrastructure`), рабочий язык русский, агентские системы claude-code + zoo-code,
> `tracking: origin`. Две особенности, из которых выросла половина трудностей: **(1)** обёртка KAIF
> здесь ПОЛНОСТЬЮ переведена на русский агентом при деплое 1.2 (тогда языковых пакетов не было);
> **(2)** файлы KAIF намеренно **вне git-трекинга** (принцип «KLAS ≠ KAIF»: фреймворк — 3rd-party
> зависимость, в репозиторий продукта не упаковывается).
>
> **Итог миграции: успех.** Механический проход прошёл без осложнений, контент владельца не пострадал
> (измерено: из 64 файлов предварительной резервной копии изменились РОВНО 2 — `.kaif/kaif.json` и
> `package.json`), `npm run kaif:check` → «52 files + 108 agent artifacts present», 26/26 скиллов на
> месте. Ручной части оказалось много, и именно о ней отчёт.

---

## 0. Как проходило обновление (маршрут)

Проект был на 1.2, то есть **без машинерии** (`.kaif/kaif-core.mjs` появился в 1.5). Скилл
`/kaif-update` 1.6 верно маршрутизировал во второй путь: положить свежий тонкий `KAIF.md` в корень,
пройти бутстрап (`KAIF-BOOT: node` → `loader written` → `loader exit 0`), а установщик обнаруживает
старый `.kaif/kaif.json` и работает как ОБНОВЛЕНИЕ (`writeIfNew`: существующее сохраняется, новое
добавляется).

```
node KAIF-LOADER.mjs --lang ru      # agents по умолчанию = все пять (решение владельца)
→ ⟳ existing KAIF 1.2 detected — running as an UPDATE to 1.6
→ ✅ KAIF 1.6 deployed mechanically (lang ru · 8 owner docs templated · 26 skills trigger-aliased)
→ ➡ ONE cognitive step remains — KAIF_UPDATE_TASK.md
```

Соотношение труда: **механическая часть — минуты, когнитивная — часы.** Обещание архитектуры 1.5
(«твоя работа — задача, а не миграция») на скачке 1.2 → 1.6 выполняется лишь частично, и трудности
ниже объясняют, почему.

## 1. Трудности — по убыванию влияния

### 🔴 T1. Legacy-путь не сообщает, ЧТО именно разошлось: `diverged = []`

**Что произошло.** В `cmdInstall` при обнаружении старого маркера задача создаётся так:

```js
writeUpdateTask([], meta, `legacy update ${legacyOld.version} → ${meta.version}: pre-1.5 project has
  no content snapshots, so every kept framework file may carry local edits — merge the 1.5 template
  news below into them pointwise`);
```

Список разошедшихся — пустой литерал. Формулировка честная («every kept file MAY carry local edits»),
но операционно она означает: *«разбирайся сам со всем деревом»*. Пункта `merge-diverged` в задаче не
появляется вовсе — остаются `review-news`, `recheck`, `judge`. Для скачка через 4 версии это 133 файла
бандла против 37 развёрнутых, и агент не знает, где из них 3 строки, а где 128.

**Почему это проблема механизма, а не проекта.** Единственная причина отсутствия слепков — что
`.kaif/deploy-manifest.json` не существовал в 1.2. Но синтетический слепок **полностью восстановим**:
машинерия знает `origin` и знает старую версию из маркера, а релизный артефакт старого тега лежит на
месте и парсится тем же кодом.

**Как обошли.** Восстановили базовый слепок 1.2 из `v1.2/KAIF.md` тем же парсером блоков
`> **FILE: \`path\`**` + шестибэктиковый фенс, что у `parseBundle()`, и продиффили против
`v1.6/dist/KAIF-CORE-BUNDLE.md`. Работа сразу перестала быть туманом и стала списком:

| | |
|---|---|
| **изменилось 15** | `AGENT_GUIDE.md` (+128/−13) · `kaif-update` (+30/−25) · `BUG_FIXING_FRAMEWORK.md` (+46/−1) · `release` (+41/−4) · `dayloop` (+28/−13) · `PHILOSOPHY.md` (+28/−0) · `nightloop` (+22/−6) · `autoloop` (+17/−7) · `bug-research` (+4) · `KAIF_FRAMEWORK.md` (+2) · `check-backlog`/`interview`/`report-bug` (+2 каждый) · `resume`/`refresh-context` (+1) |
| **новых 7** | `EXPERIENCE.md` · `TESTING_FRAMEWORK.md` · скиллы `experience`, `fable-method`, `fable-loop`, `fable-judge`, `fable-domain` |
| **без изменений 22** | 10 из 21 скилла 1.2 не изменились ВООБЩЕ; трогать их не нужно |

Инструмент оформлен в проекте как `tools/kaif-baseline-diff.mjs` (zero-deps, Node ≥18).

**Предложение.** Реализовать это в машинерии — это снимает бо́льшую часть когнитивной работы легаси-обновления:

1. При `legacyOld` (и вообще при отсутствии `shas` для пути) скачивать артефакт **старого** тега
   (`dist/KAIF-CORE-BUNDLE.md`, для ≤1.4 — `KAIF.md`) и парсить в «синтетический слепок старых шаблонов».
2. Дальше применять ровно ту же логику, что и на sha-пути: файл на диске **байт-равен старому шаблону**
   → безопасно заменить новым; отличается → в `diverged`.
3. В `KAIF_UPDATE_TASK.md` выписывать не только список разошедшихся, но и **per-file churn старый
   шаблон → новый шаблон** (`+N/−M`), потому что агенту нужно знать не «этот файл разошёлся», а «в этом
   файле апстрим добавил вот столько». Файлы с churn = 0 явно помечать как «переносить нечего».

Одно это превратило бы мои часы в минуты: 22 файла можно было не открывать вовсе, а 10 из 15 изменённых
— это правки в 1–4 строки.

### 🔴 T2. `templateNotes` в бандле 1.6 описывают 1.5 и не кумулятивны

**Что произошло.** Раздел «What's new in the templates» в сгенерированном `KAIF_UPDATE_TASK.md`
заканчивается строкой:

```
- Release codename for this version: KAIF 1.5 — Tested KAIF
```

при том, что установлена **1.6**. То есть `templateNotes` в `kaif-bundle-manifest.json` релиза 1.6 не
обновили с 1.5. Плюс структурная проблема: notes **односерийные**. Проект, прыгающий 1.2 → 1.6, видит
новинки ровно одной версии, а 1.3, 1.4 и 1.6 не упомянуты нигде. Из-за этого «review-news» как
источник истины не работает: реальным источником пришлось делать диффы (T1).

Третья, мелкая: строка контекста легаси-задачи содержит **хардкод** «merge the **1.5** template news
below» независимо от целевой версии.

**Предложение.**
1. Внести обновление `templateNotes` в релизный чек-лист `/release` (похоже, просто пропустили на 1.6).
2. Хранить notes **по версиям**: `templateNotes: { "1.3": [...], "1.4": [...], "1.5": [...], "1.6": [...] }`
   и при обновлении печатать **объединение всех версий строго между** старой и целевой. Тогда любой
   скачок через N версий информативен.
3. Убрать хардкод «1.5» из строки контекста — подставлять `meta.version`.

### 🟠 T3. «Откатываемый дифф» через git может не существовать, а скилл на него опирается

**Что произошло.** `/kaif-update` предписывает: *«Commit first so the update is a clean, revertable
diff»*. В KLAS вся обёртка KAIF в `.gitignore` осознанно (`.kaif/`, `.claude/`, `.roo/`,
`AGENT_GUIDE.md`, `PHILOSOPHY.md`, `BUG_FIXING_FRAMEWORK.md`, `AGENTS.md`, `CLAUDE.md`,
`KAIF_FRAMEWORK.md`). Значит **git не откатит из обёртки ничего**: ни `git stash`, ни
`git checkout -- .`, ни `git revert`. Гарантия обратимости, на которую опирается скилл, здесь просто
отсутствует, и заметить это нужно ДО мутаций, а не после.

**Как обошли.** Сняли файловую резервную копию всех путей, которые установщик мог тронуть (64 файла,
521 КБ) — она же потом дала точный ответ «что изменилось» (см. «Что сработало отлично», п. 1).

**Предложение.** Сделать резервную копию свойством машинерии, а не дисциплины агента:
1. Перед мутациями `update` / `install`-как-update копировать затрагиваемые пути в
   `.kaif/backup-<oldver>-<timestamp>/` (список путей у машинерии уже есть — `deployedPaths`), печатать
   путь и одну команду восстановления. Стоимость — сотни килобайт.
2. Проверять `git check-ignore` по своим путям (или просто `git status --porcelain --ignored`) и, если
   обёртка вне трекинга, **предупредить явно**: «git-откат этого обновления недоступен, страховка —
   вот эта копия». Проекты, где KAIF намеренно вне git, — не экзотика: это естественный выбор для
   любого продукта, не желающего вендорить dev-фреймворк.

### 🟠 T4. CRLF/LF обнуляет sha-снимки «файл не трогали»

**Что произошло.** Замер на живом дереве до обновления: **все 53 файла обёртки эпохи 1.2 — CRLF**
(их писал агент под Windows), тогда как машинерия 1.5+ пишет **LF** (`parseBundle` нормализует
`\r\n` → `\n`). Различие переводов строк — при полностью совпадающем смысле — делает
`fileSha(p) === oldShas[p]` ложным **всегда**.

В KLAS это не выстрелило только потому, что на легаси-пути снимков и так нет. Но на проекте, который
обновляется **1.5 → 1.6 под Windows**, достаточно одного сохранения файла редактором с CRLF (или
`core.autocrlf=true` на checkout), чтобы файл навсегда стал «diverged» — и механическое обновление
тихо выродится в ручное, без единого сообщения о причине. Апстрим эту проблему у себя знает и лечит
(`bug 03`, `.gitattributes` с `* text=auto eol=lf`) — но **в развёрнутом проекте такого пина нет**.

**Как обошли.** Привели всю обёртку к LF (44 файла нормализованы; итог — 162/162 LF) и зафиксировали
это правило в каноне проекта, отдельно оговорив, что на `.bat` (CRLF обязателен) и `.ps1` с кириллицей
(UTF-8 с BOM) оно НЕ распространяется.

**Предложение.**
1. Считать sha по **нормализованному** содержимому текстовых файлов: одна строка в `fileSha` —
   `sha256(readFileSync(p,'utf8').replace(/\r\n/g,'\n'))`. Это защищает и от редактора владельца, и от
   `core.autocrlf`, и стоит ноль.
2. Дополнительно (не вместо): при установке писать/дополнять `.gitattributes` строкой `eol=lf` для
   своих путей.
3. В `update` печатать диагностику: если файл отличается от слепка ТОЛЬКО переводами строк — говорить
   это прямо, а не относить в «diverged» молча.

### 🟠 T5. Незаполненные плейсхолдеры на update-пути теряются, а финальный гейт видит лишь две поверхности

**Что произошло (измерено после механического прохода).** В дереве остались литеральные плейсхолдеры:
`<BUILD_COMMAND>` ×9, `<TEST_HARNESS>` ×9, `<YOUR AGENT/MODEL>` ×3 (в копиях `.agents/`, `.grok/`,
`.cline/`) и `<BUILD_COMMAND>` в `.kaif/spheres/programming.md`. Это ровно те три значения, которые
`detectValues()` в KLAS не может определить механически (в `package.json` нет скриптов `build` и `test`,
а модель агента — всегда работа агента).

Две независимые причины:

1. **`unresolved` не доходит до задачи.** `cmdInstall` аккуратно собирает `unresolved`, но в
   легаси-ветке зовёт `writeUpdateTask([], meta, …)` — а пункт `placeholders` есть только в
   `writeAdaptationTask`. `cmdUpdate` тоже вычисляет `unresolved` и тоже никуда его не передаёт.
   Итог: на пути обновления агенту про незаполненные плейсхолдеры **не сообщают вообще**.
2. **Гейт не покрывает эти пути.** `scanPlaceholders()` сканирует только `AGENT_GUIDE.md` и
   `.claude/skills/*/SKILL.md`. Ни `.kaif/spheres/`, ни копии по агентским системам в область не
   попадают, поэтому `update-verify` проходит зелёным при плейсхолдерах на диске.

Заглушка, доехавшая до контента, — это ровно то мошенничество («placeholder shipped as fact»), за
которым `fable-judge` охотится по указанию самого 1.6; неприятно, что её оставляет машинерия.

**Как обошли.** Копии вылечились сами (`resyncCopies()` перезаписал их из русского канона, где
плейсхолдеров нет) — но это КЛАССОВАЯ случайность нашей конфигурации, а не работающий механизм: на
англоязычном проекте канон нёс бы те же плейсхолдеры. `.kaif/spheres/programming.md` починили руками.

**Предложение.**
1. Передавать `unresolved` в `writeUpdateTask` тем же пунктом `placeholders`, что и в задаче адаптации.
2. Расширить `scanPlaceholders()` на **всё, что перечислено в `deploy-manifest.json → paths` + `agents`**
   — список уже собран и лежит рядом, проверка стоит копейки.

### 🟡 T6. Легаси-обновление молча разворачивает все пять агентских систем

**Что произошло.** Дефолт `--agents` — все пять (`claude-code,codex,grok-build,cline,zoo-code`), это
26 скиллов × 4 копии ≈ 108 артефактов. Важно: **`cmdInstall` не читает агентов из старого маркера.**
Наследование `cur.agents` есть только в `cmdUpdate`; а у маркера 1.2 поле было в единственном числе —
`agent: "claude-code"`. Значит проект, обновляющийся бутстрапом (то есть КАЖДЫЙ проект ≤1.4), молча
получает четыре системы, о которых не просил, и ~80 лишних файлов в дереве.

В KLAS это не вред: владельцу задали вопрос, и он сознательно выбрал «все пять, про запас». Но выбор
был сделан потому, что агент заметил дефолт и спросил, — механизм на это не рассчитывает.

**Предложение.** В `cmdInstall` при `legacyOld` выводить дефолт как
`legacyOld.agents ?? (legacyOld.agent ? [legacyOld.agent] : ALL_AGENTS)` и печатать явную строку:
«разворачиваю под системы: … (переопредели `--agents`)». Тогда молчаливое расширение невозможно.

### 🟡 T7. Смена языковой архитектуры между 1.2 и 1.5+ — миграции для неё не предусмотрено

**Что произошло.** В 1.2 языковых пакетов не было: «рабочий язык — русский» означало, что агент
**перевёл всю обёртку** (все 21 скилл, весь канон). В 1.5+ модель другая и, на мой взгляд, лучшая:
скиллы остаются английскими, к их `description` дописываются `Trigger aliases (ru): …`, а по-русски
идут только owner-facing документы из `templates/languages/ru/`.

Проект, переведённый по-старому, попадает в развилку, которую **нигде не описывают**:

- принять новую модель → потерять русский текст скиллов, но получить механические обновления навсегда;
- сохранить русский → каждое будущее обновление остаётся ручным переносом.

Владелец KLAS выбрал второе, осознанно (рабочий язык проекта — русский, это принцип, а не удобство).
Цену зафиксировали письменно: в `AGENT_GUIDE.md` («Языки — осознанное расхождение с апстримом», плюс
список токенов, которые не переводятся НИКОГДА: `name:`, пути, команды, `INTENT:`/`AUTH:`/`TWINS:`/
`PENDING:`, `[NOT-TESTED]`/`[TESTED:]`/`[AI]`, `VERIFIED`/`REFUTED`, `KAIF-UPDATE:`) и в самом
`/kaif-update`, чтобы следующая сессия не «починила» перевод обратно.

**Предложение.**
1. Описать эту развилку прямо в `/kaif-update`: слабая модель не заметит, что стоит перед выбором, и
   либо затрёт перевод, либо не поймёт, почему всё «diverged».
2. Дать маркеру поле режима, например `"i18n": "translated" | "aliased"`. Тогда машинерия ЗНАЕТ, что
   расхождение намеренное, и может (а) не предлагать «починить», (б) в режиме `translated` сразу
   включать per-file churn (T1) — потому что это единственное, что делает ручной перенос выносимым.

### 🟡 T8. `KAIF-FULL.md` — подмножество, а имя обещает обратное

**Что произошло.** Мой инструмент сначала брал `dist/KAIF-FULL.md` и получил **44 файла** вместо
**133**: `KAIF-FULL.md` — офлайн-вариант и является ПОДМНОЖЕСТВОМ установочного набора (нет
`templates/languages/**`, нет `spheres/**`, нет `references/**`). Пока это не заметно, churn-отчёт
выглядит достоверным и молча врёт: например, `fable-method/references/*` попадают в «новых» или
пропадают вовсе. Нигде рядом состав ассетов не описан, а слово «FULL» уводит ровно в противоположную
сторону.

**Предложение.** Одна строка в `kaif-manifest.json` (или в теле релиза) о составе каждого ассета —
что именно внутри и для чего он. Как вариант — переименовать в `KAIF-OFFLINE.md`: «офлайн» описывает
назначение честно, «full» описывает объём неверно.

### 🟢 T9. Маркер не ведёт истории обновлений

Маркер KLAS нёс кастомные поля `deployed` / `migrated` (наша конвенция). Машинерия их **корректно
сохранила** — молодец, это неочевидная вежливость, — но своей истории не ведёт: после 1.2 → 1.6
`migrated` остался `2026-07-03`, и мы обновили его руками (сама `.kaif/kaif.json` руками правиться не
должна — на это есть команды, см. «Что сработало отлично», п. 5, — так что для собственных полей
машинерии обходного пути нет).

**Предложение.** Вести `history: [{ from, to, date, route: "core-update" | "legacy-bootstrap" }]`.
Дёшево, и делает `/kaif-version` заметно полезнее: сразу видно, откуда проект пришёл и каким путём.

### 🟢 T10. Артефакты прошлых версий остаются жить и лгут

**Что произошло.** В KLAS с эпохи 1.2 лежал `tools/kaif.mjs` — тогдашняя реализация `npm run kaif:*` с
захардкоженным списком **21** скилла. После обновления `package.json` был корректно перенаправлен на
`.kaif/kaif-core.mjs`, но старый файл остался на диске, читал новую версию из маркера и печатал:

```
✔ KAIF v1.6: структура целостна (11 документов, 6 директорий, 21 скиллов)
```

Зелёный рапорт о целостности, не знающий ни о 5 новых скиллах, ни о `EXPERIENCE.md`, ни о
`TESTING_FRAMEWORK.md`, ни о `spheres/`, ни о копиях по агентским системам. Классический ложный
`[TESTED]`. Вывели из эксплуатации, зафиксировав в каноне, что проверка структуры — только
`npm run kaif:check`.

**Предложение.** Держать в бандле список **deprecations** — артефактов, которые кладли прошлые версии
и которые новая замещает, — и на `update` либо удалять их, либо выносить отдельным пунктом задачи.
Правило общее: «механизм, заменивший другой механизм, отвечает за уборку предшественника», иначе
устаревший валидатор переживёт несколько версий и будет всё это время выдавать ложные подтверждения.

## 2. Что сработало отлично (не ломать)

1. **Уважительность `writeIfNew` — подтверждена измерением, а не на слово.** Из 64 файлов резервной
   копии после механического прохода изменились **ровно 2**: `.kaif/kaif.json` и `package.json`. Все 21
   русский скилл, весь канон, все README директорий, `CLAUDE.md`, `AGENTS.md`, `.roo/` — байт-в-байт как
   были. Контент владельца (`GOAL.md`, `STATUS.md`, `MASTER_PLAN.md`, карты, все директории знаний) в
   область обновления не попал вообще. Это главное обещание фреймворка, и оно выполнено буквально.
2. **Слияние маркера.** `sphere: ai-infrastructure`, `language: ru`, кастомные `deployed`/`migrated`
   сохранены; устаревшее поле `agent` (1.4) снято; добавлено `agents: [...]`. Ровно то поведение,
   которого хочется от миграции: двигается только то, чем владеет установщик.
3. **sha256-гейт загрузчика.** Сработал штатно; независимо сверили байты `dist/` на теге `v1.6` с
   `kaif-manifest.json` — совпали. Отказ «refusing to run it» с подсказкой про CDN-перекос на
   `--channel main` — хорошая, зрелая диагностика.
4. **Вежливая проводка `package.json`.** Три handle дописаны, существующие скрипты KLAS (`deploy`,
   `deploy:apply`, `health`) не тронуты, файл не перезаписан целиком.
5. **`checkpoint <id>` и `sphere <name>` вместо ручной правки файлов.** Правильное решение и по
   правильной причине (комментарии в коде честно ссылаются на полевые наблюдения за слабыми моделями).
   Тот же принцип стоит распространить на любые поля маркера, которые проект может захотеть обновить.
6. **`resyncCopies()` в финальном гейте — попадание в десятку для нашего случая.** Правишь ОДИН канон
   `.claude/skills/`, и 108 копий по четырём системам раскладываются сами. Без этого русификация
   26 скиллов × 4 системы была бы неподъёмной и гарантированно рассинхронизировалась бы.
7. **Единая последовательность гейтов для обоих путей** (`runFinalGates` для `verify-final` и
   `update-verify`) — верное решение: закрывающие гарантии есть свойство ДЕРЕВА, а не маршрута.
   Комментарий в коде про полевой случай на проекте `ndim` — образец того, как надо документировать
   причину правила.

## 4. Одна мысль напоследок

Архитектура 1.5 верна: механизировать всё механизуемое и оставить агенту только суждение. Единственное,
чего ей не хватает на легаси-скачках, — **знания о прошлом**. Слепки решили эту задачу для будущих
обновлений, но для уже развёрнутых проектов прошлое лежит не в проекте, а **в собственных релизах
KAIF** — и оттуда его можно достать тем же кодом, что уже написан (`parseBundle`). T1 и T4 — это, по
сути, одна идея: сравнивать надо **смысл со смыслом**, восстановив базу, а не надеяться, что база
случайно сохранилась побайтово.

## Решения, принятые без владельца

- **Нормализация обёртки KAIF к LF** (44 файла). Причина: машинерия пишет LF, апстрим пинит LF, а
  смешанные переводы строк обнуляют sha-снимки. Правило `.bat` = CRLF и `.ps1` с кириллицей = UTF-8 с
  BOM НЕ затронуто (это не файлы KAIF).
- **`references/*` скилла `fable-method` оставлены английскими** (3 файла), вопреки общему решению
  «обёртка по-русски». Причина: их ценность — байт-идентичность апстриму, дающая механическое
  обновление; это глубокий справочник, подгружаемый по требованию. Зафиксировано в `AGENT_GUIDE.md`.
- **Библиотеки сфер `.kaif/spheres/` оставлены английскими**, кроме починки одной заглушки
  `<BUILD_COMMAND>` в `programming.md` (заглушка в контенте — дефект по определению).
- **`tools/kaif.mjs` выведен из эксплуатации** (копия сохранена в резервной копии сессии). Причина —
  T10: ложный зелёный рапорт о целостности. Ссылки обновлены в `AGENT_GUIDE.md`,
  `PROJECT_STRUCTURE_EXTERNAL_MAP.md`, скилле `kaif-remove`, комментарии `tools/anonymize.mjs`.
- **Создан `tools/kaif-baseline-diff.mjs`** и внесён в `.gitignore` по правилам KAIF-обёртки. Причина:
  ручная процедура из T1 должна быть одной командой к следующему обновлению (правило харнесса из
  `AGENT_GUIDE.md`).
- **`migrated` в маркере обновлён на 2026-07-26** руками — своего механизма для этого поля у машинерии
  нет (T9).
