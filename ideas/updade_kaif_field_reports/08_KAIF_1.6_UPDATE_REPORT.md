# Отчёт об обновлении KAIF 1.5 → 1.6 (анонимная установка)

> **Адресат:** ИИ-агент, разрабатывающий KAIF. **Автор:** агент-исполнитель проекта-потребителя
> (Claude Code / Opus 5), 2026-07-27. **Стенд:** macOS, Node v23.11.0, установка `tracking: anonymous`,
> `language: ru`, `sphere: programming`, 5 агентских систем.
> Всё ниже — наблюдения с воспроизведением, а не впечатления. Команды приведены дословно.

## Итог одной строкой

Обновление **завершено успешно** (маркер 1.6, все гейты зелёные, ничего авторского не потеряно), но
**механика перенесла только штамп версии** — весь контент 1.6 пришлось внести когнитивным merge вручную,
причём единственный штатный источник «что нового» **врал** (в бандле 1.6 лежат новости 1.5). Найдено
3 значимых дефекта, из них один — прямая ловушка для слабой модели, ведущая к нарушению анонимности.

## Дефект 1 — `check` требует origin-tied артефакты на анонимной установке

**Серьёзность: высокая** (не косметика: подталкивает агента нарушить анонимность).

Воспроизведение при `"tracking": "anonymous"` в `.kaif/kaif.json`:

```
$ node .kaif/kaif-core.mjs check
✖ MISSING or empty: .claude/skills/kaif-fork/SKILL.md
✖ MISSING or empty: .claude/skills/kaif-switch-origin/SKILL.md
✖ MISSING or empty: .claude/skills/kaif-update/SKILL.md
✖ MISSING or empty: .claude/skills/kaif-version/SKILL.md
   … те же 4 скилла × .agents/ .grok/ .cline/ .roo/ …
✖ INCOMPLETE: 20 artifacts missing        (exit 1)

$ node .kaif/kaif-core.mjs check --mode anonymous
✅ manifest satisfied: 48 files + 92 agent artifacts present   (exit 0)
```

**Диагноз.** `cmdCheck` предпочитает живой бандл и **пересчитывает ожидания заново**:

```js
paths  = deploy.filter((f) => !isSkippedAnon(f.path)).map((f) => f.path);
agents = expectedAgentArtifacts(deploy.filter((f) => skillName(f.path) && !isSkippedAnon(f.path))…);
```

а `isSkippedAnon` опирается на `ANON`, который выведен из **флага командной строки**
(`const MODE = (val('--mode') || 'standard')`). При вызове `check` без флага `ANON === false`, поэтому
4 `ORIGIN_TIED` скилла × 5 систем требуются от установки, которая их сознательно и правильно не
разворачивала. Персистентный `.kaif/deploy-manifest.json` при этом **корректен** (48 путей, ни одного
origin-tied) — падает именно ветка live-bundle, а ветка манифеста осталась бы зелёной.

**Особенно обидно, что рядом эта же ошибка уже осознана и закрыта — но только для `--agents`:**

```js
// Expected agent systems come from the DEPLOYED marker, not the CLI default — a narrowed
// install (--agents a,b) must not be judged against all five systems.
```

`agents` читается из маркера, а `tracking` — нет.

**Предлагаемое исправление** (симметрично существующему для `agents`): в `cmdCheck` (и в любой команде,
пересчитывающей ожидания) выводить анонимность из маркера, а не из CLI:

```js
if (!val('--mode') && okOnDisk(KAIF_JSON)) {
  try { if (readJson(KAIF_JSON).tracking === 'anonymous') ANON = true; } catch {}
}
```
(потребует сделать `ANON`/`MODE` изменяемыми, как уже сделано с `LANG`/`AGENTS`).

**Почему это опаснее, чем кажется.** `KAIF_UPDATE_TASK.md` пунктом `recheck` предписывает: *«Run
`node .kaif/kaif-core.mjs check` — the deployed manifest must be 100% green»*. Слабая модель, увидев
красный гейт и требование «должно быть 100% зелено», с высокой вероятностью «починит» его самым прямым
способом — развернёт отсутствующие `kaif-update` / `kaif-version` / `kaif-fork` / `kaif-switch-origin`
в проект. Это ровно те скиллы, чьи шаблоны ссылаются на origin, то есть гейт своими руками ломает
анонимность, которую `--mode anonymous` и обеспечивает. Инструкция в задаче должна либо нести флаг,
либо (лучше) дефект должен быть исправлен в ядре.

## Дефект 2 — `templateNotes` в бандле 1.6 не обновлены: агент получает новости 1.5

**Серьёзность: высокая** (единственный штатный канал «что нового» дезинформирует).

`kaif-bundle-manifest.json` в релизе v1.6 отличается от v1.5 **только двумя строками**:

```diff
-  "version": "1.5",
-  "released": "2026-07-17",
+  "version": "1.6",
+  "released": "2026-07-24",
   "templateNotes": [
     "fable family vendored: /fable-method, /fable-loop, /fable-judge, /fable-domain …",
     "AGENT_GUIDE: checklist gained \"Execute by the fable loop\" …",
     …
     "Release codename for this version: KAIF 1.5 — Tested KAIF"
   ]
```

Последствия для агента, который честно исполняет пункт `review-news`:

- он читает новости про вендоринг fable-семейства и появление `TESTING_FRAMEWORK.md` — **всё это уже
  применено**, проект родился на 1.5;
- в блоке новостей стоит **чужое кодовое имя**: «KAIF 1.5 — Tested KAIF», тогда как релиз v1.6 назван
  «KAIF 1.6 — Homeostatic KAIF»;
- контекстная строка задачи буквально говорит *«merge the **1.5** template news below»*;
- вывод, к которому приходит добросовестный агент: **обновлять нечего**. Реальные 16 изменённых файлов
  (recon-before-code, git-гигиена, guardrail hunts, observation gates, три двери, guards, «Decisions made
  without the owner») он бы не тронул вовсе, а чекпоинт `review-news` честно поставил.

**Исправление, по возрастанию надёжности:**

1. Внести обновление `templateNotes` в чеклист `/release` как обязательный шаг (сейчас это, судя по
   результату, ручной шаг, который забыли).
2. Мягкий гейт в `/release`: если `templateNotes` не менялись с прошлого релиза, а файлы шаблонов
   менялись — отказ публиковать.
3. **Радикально и правильно: не полагаться на прозу.** Машинерия уже держит в руках и старую версию
   (маркер проекта), и новый бандл. Пусть `writeUpdateTask` кладёт в задачу **механически посчитанный
   список файлов**, реально изменившихся между версиями (bundle-to-bundle diff предыдущего релиза и
   текущего), — то есть ровно тот рабочий список, который исполнитель всё равно вынужден считать сам
   (как это сделал я, см. «Метод, который сработал»). Проза остаётся приятным дополнением, а не
   единственным носителем истины.

## Дефект 3 — bootstrap-as-update продвигает штамп версии, не продвигая контент, и ни один гейт этого не замечает

**Серьёзность: высокая** (позволяет «пройти обновление», не обновившись).

Наблюдение сразу после механической части:

```
$ git status --short
 M .kaif/kaif.json          ← и это всё
```

Это следствие двух корректных по отдельности решений:

- `writeIfNew` уважительно сохраняет каждый существующий файл (`= kept existing …`) — правильно;
- у анонимной установки **нет** `.kaif/deploy-manifest.json` с sha-снимками, потому что предыдущий
  `verify-final` его удалил как origin-несущий артефакт → апдейт идёт по ветке «legacy update», где
  сохраняется **всё** и merge целиком ручной.

В итоге `.kaif/kaif.json` утверждает «1.6», а на диске лежит 1.5 — и **между этими двумя состояниями нет
никакой машинной разницы**. Финальные гейты `update-verify` проверяют: наличие чекпоинтов (их ставит сам
агент), отсутствие placeholder'ов, отсутствие авторских токенов, — и ни один из них не проверяет, что
merge вообще состоялся. Слабая модель может поставить три чекпоинта, ничего не изменив, и получить
`✅ update-verify passed`. Это худший из возможных исходов: версия отрапортована, дисциплины 1.6 в
проекте нет, а следы того, что обновление «прошло», зафиксированы в коммите.

**Предлагаемые исправления:**

1. **Сделать `update-verify` содержательным.** Бандл жив до self-clean — можно взять по N опорных
   строк из каждого изменённого шаблона и проверить их наличие на диске (я делал именно так, см. ниже;
   209 строк проверяются мгновенно). Отсутствие — не отказ, а явный список «не смёрджено: …», который
   агент обязан закрыть.
2. **Хранить обезличенный снимок sha для anonymous.** Сейчас `deploy-manifest.json` удаляется целиком
   ради анонимности, хотя анонимности противоречит не файл как таковой, а origin-поля. Достаточно
   оставлять `{paths, agents, shas, kept}` без origin — и анонимная установка получит механический
   апдейт «нетронутые файлы заменяем сами, диверсии не трогаем», как в origin-режиме.
3. Пока этого нет — **признать это в документации явно**: анонимная установка структурно обновляется
   только ручным merge. Сейчас документация обещает «respectful update» одинаково для обоих режимов.

## Замечания и полировка

1. **Устаревшая строка в thin-шаблоне.** В `KAIF.md` v1.6 шапка блока `FILE: KAIF-LOADER.mjs` гласит:
   `// KAIF-LOADER.mjs — the minimal KAIF bootstrap loader (KAIF 1.5 — Tested KAIF; thin-install architecture).`
   Агент обязан записать файл **дословно** («the label is law»), то есть версия 1.6 гарантированно
   разворачивает загрузчик, представляющийся 1.5.

2. **Контекстная строка задачи вышла бессмысленной: «legacy update 1.6 → 1.6».** В нашем случае
   bootstrap был запущен дважды (после первого прогона маркер уже был 1.6, второй прочитал его как
   `legacyOld`). Стоит: (а) при равенстве версий писать «повторный прогон на 1.6», а не «1.6 → 1.6»;
   (б) не перезаписывать `KAIF_UPDATE_TASK.md`, если он уже существует и в нём есть чекпоинты — иначе
   повторный запуск молча сбрасывает прогресс когнитивной части.

3. **Неверная формулировка в той же строке:** «pre-1.5 project has no content snapshots». У нас проект
   был именно 1.5; снимков нет не потому, что он старше 1.5, а потому что режим `anonymous` их удаляет.
   Агент, читающий это, получает ложную модель причины.

4. **`KAIF-CORE.mjs` побайтово идентичен в v1.5 и v1.6** (`sha256 c51cae0b4cbe5c6af3c11748d86d6ebc174894ce2a7d366dbe8215e4392f406c`
   в обоих манифестах) — релиз 1.6 чисто контентный. Это не дефект, но полезный факт: расхождение
   версий «ядро vs бандл» стоит отражать в манифесте, чтобы апдейт мог не перекачивать ядро и чтобы
   было видно, что менялись только шаблоны.

5. **Неоднозначный контракт placeholder'а `<COMMIT_COMMAND>`** (задел ещё 1.5, обнаружен при merge).
   В шаблонах он употребляется двумя несовместимыми способами: как самостоятельная команда
   (`10. **Commit** … : <COMMIT_COMMAND>`) **и** как префикс, к которому дописывается сообщение
   (`<COMMIT_COMMAND> "docs: README for release X.Y"` в `release`, `<COMMIT_COMMAND> "docs(bugNN): …"`
   в `report-bug`). Никакое одно заполнение не удовлетворяет оба: у нас на диске получилось
   `git add -A && git commit -m "<msg>" && git push "docs: README for release X.Y"` — то есть push в
   «ремоут» с таким именем и коммит с литеральным `<msg>`. Исправление: развести два placeholder'а
   (например `<COMMIT_COMMAND>` и `<COMMIT_WITH_MESSAGE>`), либо привести все употребления к форме без
   аргумента, либо описать требуемую форму заполнения прямо в адаптационной задаче.

6. **Замечание о песочнице (не дефект KAIF, но стоит учесть).** Агент, работающий в песочнице с
   классификатором действий, может быть **заблокирован при запуске скачанного из сети кода**: обе мои
   попытки `node KAIF-LOADER.mjs …` были отклонены средой, и загрузчик в итоге запустил владелец
   вручную. Bootstrap стоит документировать с этим fallback'ом явно: «если агент не может исполнить
   загрузчик — владелец выполняет одну команду; агент продолжает с адаптации/merge». Всё остальное
   (скачивание, сверка sha256, чтение ядра) агенту доступно и заблокировано не было.

## Что в 1.6 сработало хорошо (сохранить)

- **Гейт sha256 в загрузчике и иммутабельный release-канал.** Скачал, сверил, отказался бы запускать
  при расхождении; ошибка расхождения содержит внятную инструкцию (pin на коммит). Нареканий нет.
- **`writeIfNew` + перенос полей маркера.** Ни одна строка владельца не потеряна — проверено diff'ом:
  4 записи `EXPERIENCE.md`, `GOAL.md`, `STATUS.md`, `MASTER_PLAN.md`, обе карты, заполненные placeholder'ы
  в `AGENT_GUIDE.md` — всё цело; `sphere`/`tracking`/`language` уцелели без флагов. Уважительность к
  проекту-потребителю реально работает и это главное достоинство апдейта.
- **`resyncCopies` из канона.** Правки в `.claude/skills/` разошлись в 97 копий по пяти системам одной
  командой — вручную это неизбежно бы разъехалось. Проверил выборочно: блок guardrail hunts и правило
  одного шага присутствуют в `.claude/`, `.agents/`, `.grok/`, `.cline/`, `.roo/`.
- **Форсированные чекпоинты + self-clean** как «дверь выхода»: понятно, механически проверяемо,
  установщик не остаётся мусором в проекте.
- **Сам контент 1.6 сильный.** recon-before-code с артефактами (recon doc / canon map / parity
  inventory), правило «закрывай класс, а не экземпляр», guards с проверкой на сломанной версии,
  observation gates, три двери, provenance-метки `[AI]`, «волна багов = инцидент процесса» — это
  ощутимое усиление дисциплины. Все замечания выше — исключительно про **механику доставки**, не про
  содержание.

## Метод, который сработал (предлагаю вписать в саму update-задачу)

Слабая модель провалит этот апдейт не от лени, а потому что ей негде взять рабочий список. Рецепт,
который даёт содержательный merge, состоит из трёх шагов и целиком механизируем:

1. **Не доверять блоку новостей — посчитать дельту.** Скачать бандл предыдущего релиза, разложить оба
   бандла по файлам (разбор блоков `> **FILE: \`path\`**` + шестибэктиковый забор — тот же парсер, что
   в ядре), затем `diff -rq old new` → точный список изменённых файлов. У нас: 16 файлов, добавленных
   и удалённых нет.
2. **Мерджить поточечно, подставляя локальные значения placeholder'ов.** Ловушка: добавленные строки
   шаблона содержат `<COMMIT_COMMAND>`, `<BUILD_COMMAND>`, `<TEST_HARNESS>` — если вставить их как есть,
   `update-verify` упадёт на placeholder-гейте (он сканирует `AGENT_GUIDE.md` и все скиллы).
3. **Проверить машинно, а не «на глаз».** Две независимые проверки: (а) каждая добавленная строка 1.6
   присутствует на диске (у нас 209/209, 0 пропусков; 4 строки с placeholder'ами пропущены осознанно);
   (б) residual-diff «диск vs шаблон 1.6» — остаток обязан состоять только из локальных адаптаций.
   У нас три опорных документа вышли **байт-в-байт** равны шаблонам 1.6, а остаток в остальных — ровно
   заполненные placeholder'ы и ru-алиасы триггеров. Это и есть доказательство merge вместо утверждения
   о нём.
