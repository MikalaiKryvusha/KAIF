## Вопросы

### Q1. Чем рисуем схемы?

Разведка сняла жёсткий факт: **mermaid печатается в `README.pdf` сырым кодом** (наш конвейер
`md-to-pdf` не исполняет JS), а PDF прямо назван в `GOAL.md:32`. Ещё mermaid показывает сырой
исходник в мобильных приложениях GitHub.

- **А (Рекомендовано)** — **SVG-файлы в репозитории**, по паре на схему (светлая/тёмная) через
  `<picture>`; **ноль mermaid в README**. Полный контроль брендового языка (чёрная линия, как
  `KAIF.jpg`), работает везде: GitHub, PDF, мобильный, зеркала. Цена: рисуем руками, правки дороже.
- **Б** — **mermaid** прямо в markdown. Дёшево править, диффится как текст. Цена: ломает PDF,
  ломается на мобильном, стиль навязан GitHub, композиции «было/стало» и «айсберг» недоступны.
- **В** — гибрид: SVG для 2–3 главных схем, mermaid для мелких технических. Цена: две технологии
  вместо одной (против Оккама) и PDF всё равно частично ломается.
- **Г** — свой вариант.

### Q2. Что человек видит первым — какая схема главная?

Порядок первого экрана определяет, за что цепляется незнакомец.

- **А (Рекомендовано)** — **«Было / Стало»** первой (боль и лекарство), затем «Петля» (механизм),
  затем «Просто и глубоко». Логика: сначала «зачем мне это», потом «как устроено», потом «насколько
  серьёзно». Бенчмарк: сильнейшие README открываются доказательством, а не схемой архитектуры.
- **Б** — **«Просто и глубоко»** первой: сразу отвечает на ваш бриф и отсекает «это очередной

  цифры уже измерены.

### Q4. Два языка: один файл или два?

Сейчас EN (строки 1–328) и RU (329–650) живут в одном файле. Русский читатель обязан проскроллить
всю английскую половину; переключатель языков есть **только в английской части** — существующий
дефект.

- **А (Рекомендовано)** — **разделить**: `README.md` (EN) + `README.ru.md` (RU), в шапке каждого —
  ряд языков. Так делают `biome`, `opencode`, `system-design-primer`. Каждый язык получает полноценный
  первый экран; файлы вдвое короче и проще держать синхронными.
- **Б** — оставить один файл, но починить переключатель и свернуть глубину в `<details>`.
- **В** — оставить как есть, добавить только схемы сверху (минимальное вмешательство).
- **Г** — свой вариант.

> ⚠️ Побочный вопрос к А: `README.pdf` рендерится из `README.md`. При разделении PDF станет
> английским; нужен ли `README.ru.pdf`? Рекомендую: да, вторым файлом (конвейер уже умеет).

### Q5. Что делать с 650 строками текста?

Текст хороший, но его слишком много для витрины.

- **А (Рекомендовано)** — **витрина + глубина под катом**: первый экран короткий и визуальный, весь
  справочник (таблицы навыков, документов, жизненный цикл) сворачивается в `<details>`, ссылки «наверх»
  после секций. Ничего не теряем, читать становится можно. Ориентир: ~250–300 строк на язык видимого
  текста.
- **Б** — ничего не резать и не сворачивать, добавить схемы сверху. Дёшево, но проблема «стены текста»
  остаётся.
- **В** — радикально: README = короткая витрина, вся глубина уезжает в `docs/`. Цена: новая
  директория и риск, что глубину никто не найдёт.
- **Г** — свой вариант.

### Q6. Снимать ли демо реальной сессии?

Самый сильный приём по бенчмарку (`aider`, `vhs`, `claude-code`): анимированный SVG/GIF-каст терминала.
Для KAIF это был бы **реальный прогон в этом же репозитории**: `/resume` поднимает контекст из
`STATUS.md` → работа → `/pause` записывает обратно. Подпись: «этот README ведётся KAIF'ом — вот сессия».

- **А (Рекомендовано)** — **не сейчас**: сначала схемы и структура (дёшево, полностью в наших руках),
  демо — отдельным шагом после. Не блокируем витрину записью.
- **Б** — делать сразу, вместе со схемами: без движущейся картинки первый экран слабее.
- **В** — не делать вовсе.
