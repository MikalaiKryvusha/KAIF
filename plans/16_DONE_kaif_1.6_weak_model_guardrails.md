# План 16 — Эпик KAIF 1.6: гвардрейлы для слабых моделей (идеи 15+16)

> Источники: `ideas/15_kaif_weak_model_guardrails.md` (отчёт Fable 5 по эпику «книга правил» —
> провенанс, стайлгайд, канон-карта, стражи) и `ideas/16_kaif_for_weak_models_report.md` (отчёт
> Fable 5 по сессии NDim + корпус 41 бага — разведдок, судья, гейты, деплой; обобщения уровня
> фреймворка). Оба первоисточника закоммичены дословно; переномерованы 11→15, 14→16 из-за коллизии
> с закрытыми идеями (контент не тронут). Дата плана: 2026-07-24.
>
> **Формула эпика (общая для обоих отчётов):** слабой модели нельзя доверить суждение, но можно
> доверить процедуру. KAIF 1.6 переносит качество из головы модели в механизмы: наблюдение вместо
> додумывания, список вместо прозы, гейт вместо самопроверки, видимый провенанс вместо доверия.
> Цена — скорость; выигрыш — переделки и доверие владельца.

## Цель

Сделать так, чтобы модель класса Opus, работающая по KAIF, была **надёжной** (медленнее — можно):
плохой результат (а) не попадает в канон незаметно, (б) дёшево обнаруживается, (в) дёшево
откатывается. Релиз **`KAIF 1.6 — Homeostatic KAIF`** (решение №1: фреймворк сам возвращает
процесс в здоровое состояние — как гомеостаз).

## Дизайн: 4 фазы по возрастанию цены

Обе сводки источников (ideas/15 §3, ideas/16 «Сводка») сходятся: сначала дешёвые правила-каноны и
форматы, затем судья/циклы, затем дорогие инструменты. Каждая механика попадает в ОБА слоя
фрактала (payload `framework/*` → пересборка + RU-обвязка корня), как в плане 14.

### Фаза 2 — Шаблоны и форматы знаний

- **Секция «Решения, принятые агентом без владельца»** — обязательна при закрытии в шаблонах/README
  `ideas/`, `bugs/`, `plans/` (16.7): допущения на стол владельца, генератор его вопросов.
- **Формат EXPERIENCE ужесточить под слабого читателя** (15.2.9, 16.9): обязательные поля
  «как воспроизвести проверку (готовая команда)» и «когда НЕ применять (область применимости)»;
  триггер-теги уже есть — добавить ритуал «перед задачей грепни по тегам и процитируй релевантные
  уроки или скажи "релевантных нет"» (проверяется судьёй).
- **Канон-карта домена** (15.2.3): конвенция «канон-карта до канона» — у домена с фактологией
  (мир игры, продукт, бренд, API) есть файл-карта в `researches/` (таблица сущность → роль →
  соответствие), утверждается владельцем, менять может только он; конфликт текста с картой = стоп.
  Шаблон — в README `researches/` + роутер AGENT_GUIDE.
- **Инвентарь паритета с эталоном** (16.Б): где есть эталон (старая система, конкурент, бренд-бук) —
  исчислимый чек-лист «элемент → поведение эталона → есть в новом? → OK/баг»; правило «нет строки
  инвентаря — нет кода»; судья мерит сдачу по строкам. Отличие от разведдока: разведдок описывает,
  инвентарь исчисляет.
- **Процессный документ на волну багов** (16.Е): при пачке багов от владельца агент заводит
  документ «вердикт → диагноз → лекарства → шаги» (шаблон в README `plans/`) **только по явной
  просьбе владельца** («разберись, почему столько багов») — без автоматического порога
  (решение №4); метрика здоровья — «волны мельчают».

### Фаза 3 — Судья, циклы, деплой (fable-слой и ритуалы)

- **`/fable-judge` усилить** (16.2, 16.3, 16.Г, 16.А): (а) обязателен перед каждым push и деплоем,
  не только перед «done»; (б) новая категория — «диффы, которых агент не писал» (lock-файлы,
  манифесты, сгенерированное) читаются построчно; (в) изменение `*.test.*` без блока «почему и что
  теперь стережёт» в коммите = фрод по умолчанию (усиление weakened checks до механической
  проверки); (г) охота на «литералы, похожие на данные» в диффах UI; (д) «почему этот бинарь/дамп
  в git?»; (е) сверка сдачи по строкам инвентаря паритета, где он есть.
- **Циклы `/autoloop`/`/dayloop`/`/nightloop`**: правило одного шага — одно осмысленное изменение =
  полный прогон гейтов = один коммит; пакетные коммиты на полдня запрещены (16.4).
- **Деплой-чеклист** (новая секция `/release` или отдельный шаблон; 16.5, 16.6): (1) деплой-зеркало —
  снять фактическую конфигурацию работающего прода ДО замены, каждое отличие нового запуска —
  осознанное решение; (2) смоук живого процесса с чтением лога; (3) самодостаточность артефакта
  (образ/бандл стартует в изоляции); (4) инварианты домена — числа до/после; (5) после выката —
  обновить в репо документ «боевой запуск».

### Фаза 4 — Конвенция провенанса (инструменты — эпик 1.7, решение №2)

В 1.6 входит только **конвенция** провенанса (15.2.1 — «самое важное» по цене переделок):
маркеры `[AI]…[/AI]` (написано ИИ) / `[AI-ed]…[/AI-ed]` (текст владельца, правленный ИИ) —
канонические EN-строки, greppable, как `[NOT-TESTED]`; правило «ИИ помечает всё, что пишет в
канон-артефакты владельца; пометка = очередь на приёмку; снимает её только слово владельца»;
проверка в 1.6 — грепом/глазами. Вписать в AGENT_GUIDE + PHILOSOPHY + строку фрода для judge
(«снял пометку сам» / «непомеченный ИИ-текст»).

**Инструментальная часть выделена в эпик 1.7 — `plans/17_kaif_1.7_guardrail_tools.md`**:
`kaif-provenance` (git-базлайн, `--mark`/`--check`/`--accept`, реестр принятых), скилл
`/derive-styleguide`, шаблон линтера канон-артефактов, режимы строгости «черновик»/«канон».
Предпосылка старта 1.7 — полевая обкатка конвенций 1.6 на реальном канон-проекте.
