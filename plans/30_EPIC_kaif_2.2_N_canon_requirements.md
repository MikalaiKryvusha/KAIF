> §11.2 (29148 · NASA Appendix C · EARS/Kiro · fit criterion/Гилб · ADR/MADR/RFC 7322 ·

> **Постановка владельца** — идея 20 пп. 13, 15 (10 критериев IEEE 830/29148 с примерами ❌/✅
> даны в скоупе дословно), 4, 18, 16.
> **Создан:** 2026-08-07. **Статус:** мета-план; детально расписана фаза N1 (операционка —

**Формула эпика (слова владельца):** «Без критериев приёмки и цевтора целей идеи положенные в
документы являются бессмысленными спекуляциями… С критериями приёмки и векторами целей —
становится понятно, какую "боль" и проблему хотим решить, где хотим оказаться, и чем измеряем
условия достижения желаемого — наши планы становятся проверяемыми». Плюс: насыщение документов
метой «для лучшей просматриваемости истории в очень масштабных и долгих проектах» и чёткая
таксономия документов и «контуров».

---

## Вектор цели

Каждый целевой документ KAIF открывается вектором цели и критериями приёмки; каждое требование
пишется и проверяется по стандарту (29148-дистилляция + стоп-словарь + нотация); каждый документ
несёт линтуемую шапку-мету; таксономия документов и контуров развёрнута явно — и всё это
проверяют линтеры и судья, а не благие намерения.

## Критерии приёмки эпика (наблюдаемые)

1. `REQUIREMENTS_FRAMEWORK.md` — 14-й ключевой документ поставки (подтверждение — Q9 интервью
   007): шаблон в `framework/`, полный круг доставки (EXP-0003: embed-маркер + DOC_TARGETS +
   docNames; манифест · карта модулей · README обеих половин · help-kaif · языковые пакеты);
   сборка печатает 14 документов; полигон зелёный.
2. Стоп-словарь непроверяемых слов (RU+EN, база — NASA Appendix C + смеллы Femmer) существует
   КАК СТРАЖ (греп-линтер), доказан красным на заведомо плохом требовании.
3. Шаблоны целевых документов (/plan-task, /plan-epic, /report-bug, /propose-idea + README
   plans/bugs/ideas) открываются блоком «Вектор цели + Критерии приёмки»; наши планы 2.2 уже
   исполняют это (dogfooding досрочно — проверка грепом по plans/26–36).
4. Шапка-мета: фиксированная схема (6–8 полей, YAML-frontmatter или эквивалент; «каждое поле
   либо линтуется, либо не нужно»), линтер схемы, применение к документам обвязки БЕЗ порчи
   рендера (греп-страж класса EXP-0018 прогнан).
5. Таксономия документов (ключевые-перечитывания / расширенные / рабочие / прочие / проектные)
   — в каноне; множества «ключевые документы ПОСТАВКИ» и «ядро обязательного ПЕРЕЧИТЫВАНИЯ»
   разведены явно; ярус перечитывания потребляется эпиком O.
6. Термин «контур» канонизирован (определение владельца из идеи 20); инвентарь контуров KAIF
   составлен с оценкой чёткости границ; размытые границы либо причёсаны, либо зафиксированы
   осознанным долгом.
7. Судья: критерии качества требований работают ЛИНТЕРОМ и рубрикой судьи — НЕ входным
   шлагбаумом перед началом работы (антипаттерн DoR из §11.2 не воспроизведён).

## Фазы

### N1. REQUIREMENTS_FRAMEWORK.md — документ и доставка (детальный операционный план)

- [ ] N1.1. Черновик шаблона `framework/REQUIREMENTS_FRAMEWORK.md` (EN; RU-копия в корень как
      обвязка): ядро — 10 критериев владельца (идея 20, п. 15 — вносится с минимальной
      редактурой, источник помечается) со ссылкой на нормативный якорь ISO/IEC/IEEE 29148:2018
      (9 характеристик требования + 5 набора — карта соответствия списку владельца);
      дистилляция NASA Appendix C (shall/will/should; активный залог; одна мысль);
      **стоп-словарь непроверяемых слов RU+EN**; нотация EARS (5 паттернов с русифицированными
      ключевыми словами: КОГДА / ПОКА / ЕСЛИ…ТО / ГДЕ + ДОЛЖЕН) как рекомендованная форма;
      формула критерия приёмки = fit criterion (+ триада Scale/Meter/Target для числовых);
      типизация целей Achieve/Maintain/Avoid (из KAOS, без его формализма); нормативная
      модальность по RFC 2119/8174 (нормативно только явное ключевое слово).
- [ ] N1.2. Границы документа (что он НЕ делает): не DoR-шлюз (проверка — линтером и судьёй
      ПО ХОДУ, не запретом начинать); не BDUF (требования пишутся инкрементально, по фазе);
      не Gherkin-везде (примеры-сценарии только где поведение того стоит).
- [ ] N1.3. Доставка: три точки сборки (EXP-0003) + манифест + карта модулей + README обеих
      половин (таблица документов: +1 строка) + help-kaif ×2 + KAIF_REFERENCE §доки +
      CLAUDE.md-шаблон + языковые пакеты (алиасов у документа нет, но списки документов в
      owner-доках пакетов — проверить) + счётчики пересчитает сборка.
- [ ] N1.4. Стоп-словарь как страж: скрипт-линтер (греп-ступень; вход — целевые документы
      проекта), доказан красным на фикстуре с «гибкий/удобный/as appropriate/etc.», зелёным на
      чистой; регистрация в полигоне.
- [ ] N1.5. Верификация фазы: сборка печатает 14 ключевых документов; песочница разворачивает
      REQUIREMENTS_FRAMEWORK; судья фазы (включая проверку «не создан второй канон рядом с
      TESTING_FRAMEWORK» — граница: TESTING проверяет СДЕЛАННОЕ, REQUIREMENTS формирует
      ТРЕБУЕМОЕ).

### N2. Вектор цели + критерии приёмки — в шаблоны и навыки (скелет)

Блок «Вектор цели + Критерии приёмки» ПЕРВЫМ в шаблонах: /plan-task (уже имеет «Готово,
когда» — переименовать/усилить по канону N1), /plan-epic (мета-план начинается с вектора цели
эпика), /report-bug (критерий приёмки фикса), /propose-idea (какую боль решает + как проверим);
READMEs plans/bugs/ideas; канон-строка в AGENT_GUIDE; явная оговорка модифицируемости («не
истина в последней инстанции — меняются по мере работы», слова владельца). Dogfooding-проверка
грепом по нашим планам 2.2.

### N3. Шапка-мета документов (скелет)

Фикс-схема полей (кандидат, вход фазы — утвердить на судье фазы: `что это · создан (кем/когда/
зачем) · родитель/наследники · читатели · статус · история правок (кратко) · что уйдёт вовне`);
решение «полная шапка vs лёгкая» ПО ЯРУСАМ таксономии (ключевым — полная, рабочим — короткая) —
церемония не перевешивает работу; линтер схемы; массовая правка наших документов с греп-стражем
EXP-0018 (`^[+*] ` и врап-класс) и чтением записанного обратно.

### N4. Таксономия документов + термин «контур» (скелет)

Канон-секция таксономии (5 ярусов владельца, идея 20 п. 18) с явным разведением «поставка» vs
«перечитывание» (находка §5 researches/15); ярус перечитывания — вход эпика O. Термин «контур»:
определение (граница · правила · исполнительный слой · контроль качества) в канон; инвентарь
контуров KAIF (интерактивный · обновления · обратной связи · планирования · аудита · циклов);
оценка границ; исполняется ПОСЛЕДНИМ в эпике — когда контуры 2.2 оформлены.

### N5. Линтер требований, полигон, судья (скелет)

Линтер N1.4 расширяется на требования в целевых документах (грепы стоп-словаря + наличие блока
вектора цели); полигон-свод; финальный судья эпика (включая антипаттерн-проверку: линтер
консультирует, не блокирует старт работы).
