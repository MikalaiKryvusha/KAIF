> **Родитель:** `plans/32_EPIC_kaif_2.2_P_skill_rename.md` → фаза P1 (якорь: «### P1. Схема
> имён и rename-карта»). **Создан:** 2026-08-07. **Вовне:** —. **Статус:** готов к исполнению — гейт Q4 СНЯТ
> (решение №35: все навыки KAIF → `kaif-*` КРОМЕ вендоренных fable-*; короткие старые имена —
> триггер-алиасы).

## Вектор цели

Полная машиночитаемая rename-карта «старое имя → новое имя → класс миграции» по утверждённой
схеме №35 — единый источник для payload-переименования (P2), миграции машинерией (P3) и
языковых пакетов, покрывающий все навыки без изобретения имён сверх схемы.

## Готово, когда (критерии приёмки)

1. Инвентарь всех навыков `framework/skills/` с классификацией: lifecycle `kaif-*` (уже с
   префиксом — без изменений) · вендоренные fable-* (НЕ переименовываются — №35; шапки
   атрибуции не трогаются) · остальные → `kaif-<старое имя>`; счёт строк карты = счёту навыков
   из вывода сборки.
2. Rename-карта (машиночитаемый JSON в поставку): старое → новое → класс миграции (простой
   rename / rename+semantic — для навыков, чьи тела меняются эпиками K/M в этом же релизе,
   сшивка с их диффами названа).
3. Алиасы: короткие старые имена сохранены триггер-алиасами (№35) — план обновления ключей
   9 языковых пакетов той же картой; реестр пар «состав навыков ↔ ключи пакетов» учтён.
4. Судья фазы: «ни одно имя не изобретено сверх схемы №35» (граница идентичности — имена
   образуются механически префиксом, не выбором агента); карта покрывает все навыки; закрытие
   P1 в родителе; операционный план P2 написан по урокам P1.

## Шаги

- [ ] 1. Инвентарь (критерий 1): `ls framework/skills` + классификация таблицей «текущее имя →
      новое по №35 → класс → риск».
- [ ] 2. Rename-карта JSON (критерий 2) — формат согласовать с P3 (потребитель — KAIF-CORE
      update): поля oldName/newName/migrationClass/notes.
- [ ] 3. Алиасный слой (критерий 3): схема обновления skill-triggers.json 9 пакетов картой;
      прогон команды реестра пар на текущем дереве (базовая линия до переименования).
- [ ] 4. Судья фазы (критерий 4); закрытие в родителе + план P2.

## Верификация

Критерий 1 — счётом против вывода сборки; критерий 2 — валидацией JSON скриптом; критерий 3 —
командой реестра пар; критерий 4 — судьёй.

## Риски

1. Имя сверх схемы (идентичность) → правило «новое имя = kaif- + старое», исключения только из
   №35; любое отступление — точечный вопрос владельцу, не решение агента.
2. Коллизия с lifecycle-навыками (kaif-update уже существует) → инвентарь шага 1 ловит; такие
   навыки в карте с классом «без изменений».
3. Семантические правки K/M пересекутся с rename → класс rename+semantic в карте + порядок
   эпиков (P после содержательных — №37) делает диффы K/M входом P, не конфликтом.
