## F3 — Дорога bootstrap-обновления НЕ fail-closed на незавершённой задаче: поставка НОВОГО интервала не пишется никуда, а маркер, расписка и history уже переведены на новую версию

**1. Цитата.** `framework/installer/KAIF-CORE.mjs:1786`:

```js
    if (existsSync(UPDATE_TASK) && /^KAIF-UPDATE: /m.test(readFileSync(UPDATE_TASK, 'utf8'))) {
```

Ветка срабатывает по НАЛИЧИЮ чек-поинтов, не по интервалу версий. Фикс ложится в `cmdInstall`,
тот же файл.

**2. Сценарий провала.** Воспроизведено вживую (песочница скептика, реальный dist-бандл 2.1 + два
синтетических 2.2/2.3):

1. свежий `install` 2.1;
2. владелец правит абзац в модуле — обычная законная дивергенция;
3. `bootstrap` на 2.2 → задача с конфликтным диффом;
4. агент записывает ОДИН чек-поинт (`checkpoint review-news`) и сессия обрывается;
5. позже владелец кладёт 2.3 и повторяет `bootstrap` — **для анонимных и pre-1.5 развёртываний это
   единственная дорога обновления**.

Наблюдение на диске: `= kept existing KAIF_UPDATE_TASK.md (it carries recorded checkpoints — not
overwritten)`; H1 задачи по-прежнему `finish the update to 2.2`; `grep -rl "UPSTREAM-NEWS-2.3"` —
**ни одного файла**. Апстрим-правка 2.3 в отредактированном владельцем модуле не поехала никуда, а
маркер, расписка и history уже говорят 2.3, и `update-verify` зеленеет по чек-листу ЧУЖОГО
интервала.

**3. Severity.** impact ВЫСОКИЙ (необратимая молчаливая потеря всей когнитивной поставки интервала:
нормы, policy-changes, диффы конфликтных модулей — плюс фальшивое «обновление проверено») ×
likelihood СРЕДНЯЯ (нужен ровно один прерванный bootstrap с записанным чек-поинтом) → **Act**.

**4. Базовая линия.** `новая`. Аттестация: соседние комментарии закрывают ДВА СМЕЖНЫХ случая, а не
этот — `:1784-1785` про ПОВТОРНЫЙ прогон той же версии (`bugs/14`), `:1799-1802` про задание
прошлого интервала БЕЗ чек-поинтов (`bugs/25`, judge F1). Пересечение «прошлый интервал + есть
чек-поинты» не покрыто ни одним из них.

**5. Эскиз фикса.** Разделить ветку по ИНТЕРВАЛУ, а не по наличию чек-поинтов. При
`legacyOld.version !== meta.version` применить механизм, который код уже имеет строками 1803–1807:
сохранить существующую задачу как `KAIF_UPDATE_TASK.superseded.md` с громкой строкой лога и
сгенерировать задачу нового интервала. Ветку «kept existing … carries recorded checkpoints»
оставить ТОЛЬКО для re-run (`legacyOld.version === meta.version`). Альтернатива той же цены —
fail-closed по образцу строки 1154: до любых записей отказать с кодом 1, назвав два законных хода.

**6. Фикс принят, когда.** Репро из сценария (install 2.1 → правка модуля → bootstrap 2.2 →
`checkpoint review-news` → bootstrap 2.3) даёт ОДНО из двух: либо `head -1 KAIF_UPDATE_TASK.md`
печатает «finish the update to 2.3» И `grep -rl UPSTREAM-NEWS-2.3 . --exclude-dir=.git` находит
файл (задачу или `*.superseded.md`), либо команда завершается ненулевым кодом и НЕ трогает
`.kaif/kaif.json` и `.kaif/last-update.json`. **Сегодняшнее измеренное состояние:** задача говорит
2.2, grep не находит ничего, маркер уже 2.3 — то есть оба исхода сегодня ложны, и критерий
различает починку от текущего поведения.

**7. Не трогать.** Re-run на ТОЙ ЖЕ версии обязан по-прежнему сохранять существующую задачу
побайтно и не перегенерировать её (`bugs/14`, строки 1788–1794). Задача предыдущего интервала БЕЗ
чек-поинтов обязана по-прежнему и сохраняться в сторону, и перегенерироваться (строки 1803–1807).
Ветка удаления/сохранения `TASK_FILE` (1831–1841) не меняется.
