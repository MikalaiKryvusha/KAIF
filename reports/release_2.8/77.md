Shipped in [KAIF 2.8 — Noble KAIF](https://github.com/MikalaiKryvusha/KAIF/releases/tag/v2.8):

Both faces of your ticket came from the scan walking the file system with a hand-kept deny-list. 2.8 replaces that walk:

- **One walker, and it sees the tree git sees.** The scan reads the files that `git ls-files --cached --others --exclude-standard` lists: tracked plus untracked, never ignored.
  - Your `build/wt-*` (ignored by `.gitignore`) and `.claude/worktrees/*` (excluded) are not listed.
  - A nested repository that is not ignored is listed by git as a directory entry and skipped: it is not your project.
  - A path under `.claude/worktrees/` is dropped by name even where git would list it.

  The 20-file cap is now spent on your real files, and the journal copies (an `EXPERIENCE.md` or `PROJECT_HISTORY.md` inside a copy) are never reached.
- **Nothing reads as clean when it was not seen.** A broken link is skipped with its name (`walk: skipped N unreadable path(s) — …`). If the walk could not read a directory or a file, the item says the scan could NOT see the whole tree instead of "no lines found". An unreadable file is named, never a stack trace.
- **The same walker everywhere.** One block (`KAIF-WALK`) is carried byte for byte by the core's stale-claims and anonymity scans and by the six tool modules that walk the tree: `kaif-provenance`, `kaif-canon-lint`, `kaif-requirements-lint`, `kaif-guard-lint`, `kaif-attribution-lint` and `kaif-scenario-lint`. The origin's build refuses a copy that has drifted.
- **A project that lives inside a worktree is still scanned.** A copy is judged by the path below the root being walked. A session running inside `.claude/worktrees/<agent>/` (subagent isolation) therefore still has its own files scanned.
- **NEW command `node .kaif/kaif-core.mjs stale-claims`** re-runs the scan read-only, with the interval taken from your last update receipt. "Fix these, then re-run" no longer needs a checkpoint.

What you do: on the `update` route, the 2.7 → 2.8 task item is written by your outgoing 2.7 core with its old walk, so that one item will list the worktree copies again. Read the scan through `node .kaif/kaif-core.mjs stale-claims` instead, or through `checkpoint stale-claims`, which the delivered core executes. Your worktrees stay as they are; nothing needs deleting.

Proof:
- Sandbox suite `tools/sandbox/s29-scanners.mjs`:
  - W1: a git tree with 20 copies under `.claude/worktrees/` and two broken links. The real `README.md` line is named, no path under `.claude/worktrees` appears, the item says "skipped 2", and `kaif-provenance check` exits 0 instead of a stack trace.
  - W2: the same tree without git.
  - W3: the failed-walk branch.
  - W4a–W4f: an unreadable file is reported as a failed walk by the core and the modules, and a project under `.claude/worktrees/<agent>/` has its files judged.
  - On the 2.7 core, W1–W3 fail six checks.
- The mutant probe `tools/sandbox/probes/sc-mutants.mjs` runs 19 mutants, each red exactly on its named cases.
- Functional run, read-only, on four real field trees. In the one with 13 worktrees:
  - The old walk saw 250,967 files, 184,973 of them inside the copies. The new walk sees 2,109 files and none of the copies.
  - `kaif-provenance check` went from 313 findings (287 in the copies) to 26, the same 26 real ones.
- Run reports: `testcases/reports/2026-09-26_sc1-one-safe-walker.md`, `testcases/reports/2026-09-26_sc4-read-side-fixes.md`.

Limits:
- `SKIP_FILES` is still matched by the full relative path. The nested-copy case is gone because copies are no longer walked, not because that match changed.
- The cap line keeps its form ("shown 20 of N"). Ignored paths no longer enter the count, so there is nothing to split.
- Without git (not a work tree, or no git on PATH), the fallback walk skips `.git`, `node_modules` and `.claude/worktrees` by name. A nested checkout anywhere else is recognised only when git lists the tree.
