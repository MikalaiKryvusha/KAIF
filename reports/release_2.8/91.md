Your analysis was exact. The adjacency rule written for prose had been carried into scripts, where it named the comments and missed the constant. In 2.8 the stale-claims scan (`scanStaleClaims` in `.kaif/kaif-core.mjs`) judges a script pin in the code's own vocabulary:

- **A pin is named by its identifier.** The rule applies in a script that names the framework, meaning the word `kaif` appears in its path or its text; your `tools/kaif.mjs` qualifies.
  - A quoted old version assigned to, or compared with, an identifier that names a pin is a claim. The identifiers include `EXPECTED_VERSION`, `REQUIRED_KAIF_VERSION`, `pinnedVersion`, `kaifVersion`, `KAIF_VERSION`, `FRAMEWORK_VERSION`, `KAIF_REQUIRED` and `kaifMin`.
  - In a script that reads `kaif.json`, a `.version` compared with, or asserted against, a quoted old version is a claim too: `assert.equal(marker.version, '2.7')`.
  - Your line `const EXPECTED_VERSION = '2.4';` is named.
- **A bare `version` is not a pin.** It is the product's own version or an XML attribute. The first build named `'<?xml version="1.0"'` on a real tree, and that is where this rule came from.
- **A date in a trailing comment** no longer silences a pin on the same line.
- **Comments like `// KAIF 2.4: …` are still named.** The framework's word and an old version stand as a pair. If such a comment is history, mark it once with `KAIF-VERSION-OK: <reason>` on the line or the line above, and it stops coming back.
- **NEW command `node .kaif/kaif-core.mjs stale-claims`** runs the scan read-only, with the interval taken from your last update receipt.

What you do: after the update to 2.8, run `node .kaif/kaif-core.mjs stale-claims` before your own `npm run kaif:check`. Ticking `checkpoint stale-claims`, which the delivered core executes, does the same. On the `update` route the 2.7 → 2.8 task item is written by your outgoing 2.7 core with the old rule, so it will not name the pin; the delivered core's scan will.
