Shipped in [KAIF 2.9 — Distilled KAIF](https://github.com/MikalaiKryvusha/KAIF/releases/tag/v2.9):

- **A root file git ignores is not read.** In the default scope `kaif-attribution-lint` now takes the root `*.md` from the same git-aware walk as the directories, `kaifWalk([root])` over `git ls-files --cached --others --exclude-standard`. It no longer uses `readdirSync(root)`. A root file git ignores, such as a private voice portrait, is not in the set and is never scanned. Without git the walk lists the disk, as before. One more consequence: the root file set no longer depends on whether an ignored file happens to be on disk, so a `git archive` rehearsal and the live tree scan the same root files.
- **The baseline never holds the text of a line.** `.kaif/attribution-lint.baseline.json` now maps `file:sha16(line)` to a COUNT, a fingerprint and a number, with no line text and no line number. The write message says so: "the file holds fingerprints and counts, never the text". A 2.8 baseline with text values is read as the same debt. The next `--write-baseline` by the 2.9 module drops the text.

What your side does: after the update, run `node .kaif/tools/kaif-attribution-lint.mjs check --write-baseline` once and commit the rewritten `.kaif/attribution-lint.baseline.json`. That removes the line texts your 2.8 baseline still carries. The run is refused if it would turn a NEW finding into debt, as before.

Proof: the module's `node .kaif/tools/kaif-attribution-lint.mjs selftest` has 39 cases, five of them new for this ticket and #112. They include a hidden root file with "the owner decided …" that is not read, and a baseline that holds no word of a finding's text. Probe `tools/sandbox/probes/pv-red-on-v28.mjs`: "v2.8: 4 red · this build: 0 red". Sandbox suite `tools/sandbox/s24-attribution-lint.mjs` is green. On git clones of 11 live deployments (probe `tools/sandbox/probes/pv-field-baselines.mjs`, "ALL OK"), five deployments had a git-ignored root `*.md`. The v2.8 module read it, this build does not, and the file counts differ by exactly the number of hidden files. After a write no baseline held text, and no recorded debt was lost. Run report: `testcases/reports/2026-10-16_pv-private-stays-out.md`.

Boundaries, said plainly: the fix covers the default scope. A path you name explicitly is still read, even when git ignores it: `check AUTHOR_STYLOMETRY.md` reads that file. The release's court recorded this as a finding for the next version. The text of a 2.8 baseline stays in that file, and in your git history, until the first 2.9 write; the module does not rewrite history.
