## §3. Пункт 3 — «Голос владельца» (эпик C)

  цитатами-эталонами), а не вкусов («пиши строго»).

- **Несущие гейты:** гейт корпуса (≥2 независимых завершённых текста, ~15–20 тыс. слов, ≥1 в жанре
  целевого артефакта — иначе только «черновые наблюдения») · пороги достаточности портрета (≥10

## §4. Пункт 4 — интерактивный контур согласований (эпик D)

Отчёт 13 — фактура ЖИВОГО контура (Nogamelabs, KAIF 1.6, «Мне нравится. Получилось удобно»):
md → страница → сигнал → решение кликом → механический гейт перед отправкой; ноль внешних
зависимостей; 46 самопроверок. Главные уроки для методологии 2.1:

- **«HTML — не цель, а транспорт. Цель — страж.»** Правило «все вопросы владельцу — строго в
  интервью» нарушалось агентом, который его знал (2 раза за день, ловил владелец); первый прогон
  механического стража нашёл 2 никем не увиденных вопроса, висевших 5 и 13 дней. Рекомендация №1:
  требовать **два артефакта** — рендер И страж, страж первым. Норма ложных срабатываний для стража
  текстового правила ~10:1 — исключения явные, с причиной в строке.
- **Инварианты I1–I7** (методология обязана ТРЕБОВАТЬ): I1 md — источник, HTML — производное ·
  I2 ответ в три места (исходный md · `<имя>.decision.json` · копия в reviews/ с by/at) ·
  I3 одобрение привязано к SHA-256 ТЕЛА (+ обязательная договорённость о нормализации — самый
  дорогой урок: расхождение по хвостовому `\n` при зелёных покомпонентных self-test'ах) ·
  I4 гейт на стороне ОТПРАВКИ, fail-closed · I5 сигнал после успешно открытой страницы ·
  I6 тишина перебивает всё (тихие часы пересекают полночь — отдельный страж) · I7 для автоциклов —
  накопление (`reviews/pending/` + одна страница «Накопилось N»), а не блокировка.
- **Контракты имён вместо проектирования инструментов** (рекомендация №5): нормативная часть =
  инварианты + контракт (блок метаданных: title/kind/artifacts{id,target,format,body_file-ссылка};
  запись решения: kind/document/by/at/comment + answers/artifacts) — «как построить» остаётся
  проекту. `body_file` — ссылка, не копипаста (вторая правда ломает I3).
- **Порядок работ** (их — «наш был хуже»): страж → рендер+запись решения → гейт отправки →
  сигнализация → накопление → пилот на настоящих данных. Критерий приёмки: «полный цикл рутины
  проходит без единого уточнения в чате».
- **Грабли в канон:** инструмент не внедрён, пока нет команды, показывающей нарушение (агент
  вернулся к чату в день запуска страницы) · exit 0 ≠ сигнал дошёл (уведомление глушится
  настройками ОС — подтверждать доставку у человека) · прогон по ВСЕМ живым документам — условие
  сдачи (фикстуры не ловят) · рендер в обеих темах ОС · `\w`/`\b` в Node ASCII-only — для
  кириллицы `\p{L}` с флагом `u`.
- **Границы поля:** только macOS, один владелец, локальный репозиторий, дни эксплуатации.

## §5. Пункты 5+7 — границы суждения агента (эпик E)

**Отчёт 17 (вкус):** канон покрывает измеримое (`TESTING_FRAMEWORK`) и развилки видения
(`/interview`) — и молчит про **субъективно-перцептивный критерий** («красиво», «естественно»).
Инцидент: три подряд неверных хода при выборе голоса (оптимизация не под тот критерий → чужие
бенчмарки вместо звука → битые ссылки вместо артефакта). Предложение: третий класс задач «критерий
вкуса» (грепается: прилагательное восприятия в критерии приёмки) → агент не выносит вывод, а
**производит МАКЕТ и заводит домашку**; цикл «найти → быстро макетировать → отдать артефакт (не
ссылку!) → зафиксировать вердикт как канон»; в шаблон домашки — поля «что уже можно
слушать/смотреть» и «вынесенные вердикты» (9 вердиктов за 20 минут — без записи пропали бы);
возможный навык `/mockup` (или расширение `/propose-idea`); контракт сравнения: один материал,
вслепую, расшифровка рядом.

**Пункт 7 (идентичность; отчёт 20):** агент под «НА ВСЁ ДАЮ ДОБРО» сам придумал кодовое имя релиза.
В канон: (а) различение «разрешение на ДЕЙСТВИЕ» vs «авторство ИДЕНТИЧНОСТИ» — явный концепт;
(б) именование (кодовые имена, названия, слоганы, брендовые строки) — НИКОГДА не решение агента,
ни при каком объёме одобрения; (в) правильный ход — сделать всё остальное и задать ОДИН точечный
вопрос про имя; (г) запасной выход — нейтральный фактический заголовок (имя-заглушка выходом НЕ
является); (д) у имени — свой артефакт с источником («владелец, чат, дата»). Родство с п. 5: там не
хватило смелости спросить, здесь — различения, что вопрос вообще вкусовой.

Нюансы отчёта 20 сверх пересказа в идее 19 (из верифицированного извлечения): структурная причина —
у имени релиза **не было своего артефакта/места проверки** (версия и тесты проверяются, имя — поле
свободного текста без точки, где видно, что у поля нет автора); самое переносимое — методология
умеет требовать доказательства, но не умеет требовать **АТРИБУЦИЮ** (запись, кто автор решения у
каждого внешнего артефакта); поучительная развязка — агент НЕ стал переименовывать релиз по своей
инициативе («исправление брендовой ошибки — тоже брендовое решение») — эту дисциплину сохранить как
канон; гейт нужен не на «спроси», а на «у этого поля нет автора — остановись».

Примечательно: оба правила канона существовали и были прочитаны в той же сессии — не сработали.

## §7. Пункт 6 — защищённый цикл (эпик G)

Постановка владельца: цикл как /autoloop//dayloop//nightloop, но агент организует себе

проекта дёргают агента** — сторож не внутри зависшего процесса, а снаружи. Замечание из нашей

## §11. Индустриальная разведка (гуглёж; 4 направления, по источникам)

### 11.1 Стилометрия (→ эпик C)

- **Ядро авторского сигнала — служебные слова и частотные паттерны**, не лексика содержания:
  Burrows Delta (z-оценки частот самых частотных слов; Programming Historian, Burrows 2002);
  вариации Delta почти не важны — важна стандартизация и нормализация векторов (Evert/Proisl).
- **Символьные n-граммы — сильнейшее одиночное семейство**, и сила сидит в аффиксах и пунктуации
  (Sapkota et al., NAACL 2015) — авторский стиль = привычки словообразования и знаков.
- **Многослойная таксономия признаков** (Stamatatos, JASIST 2009): лексика · символы · синтаксис ·
  прикладные маркеры; комбинации стабильно сильнее одного семейства.
- **Порог корпуса: ~2500–5000 слов на автора, метод-независимый** (Eder, DSH 2015) — ниже атрибуция
  определяется шумом. Согласуется с гейтом корпуса отчёта 22 (15–20 тыс. слов — с запасом).
- **Оценка только cross-topic** (PAN 2015+; topic leakage — arXiv 2407.19164): при пересечении тем
  меряется тема, а не автор; STEL (EMNLP 2021) — контент-контролируемая оценка стиля.
- **LLM-имитация:** few-shot до 23.5× лучше zero-shot, completion-промпт (продолжение подлинного
  текста) — почти идеален (arXiv 2509.24930); судить имитацию AA/AV-классификаторами и метриками,
  не впечатлением (arXiv 2509.14543). **Потолок честно знать:** GPT-«Хемингуэй» разнообразнее
  Хемингуэя — LLM систематически «улучшает» автора, дрейфуя к generic (DSH 2025).
- Инструментарий-референс: stylo (R), faststylometry (Python); сама математика Delta тривиальна —
  проектный Node-скрипт её осилит (KAIF инструменты не поставляет — методология называет метрику).

**Вывод для C:** методология отчёта 22 научно состоятельна (цитаты-эталоны ≈ few-shot/completion;
анти-портрет ≈ борьба с дрейфом к generic; пороги ≈ порог Эдера) — добавить из науки: гейт размера
корпуса числом (~5000+ слов минимум), машинные эвристики мерить по служебным словам/пунктуации, а
не катчфразам (катчфразы темозависимы — антипаттерн), слепой тест = наш аналог AV-оценки.

### 11.2 Human-in-the-loop согласования (→ эпик D)

- **Propose/commit-разделение** — самый надёжный паттерн: предложение = долговечный документ со
  статусом (pending→approved/rejected), исполнение — только после решения (совпадает с I1–I4
  отчёта 13). **Риск-тиринг:** гейт только на необратимое/внешнее (Permit.io); у KAIF уже есть в
  форме стоячей авторизации коммитов vs AUTH на релизы.
- **Четыре типа решения** Approve / Reject-с-причиной / Edit / Respond (LangChain HITL) — богаче
  бинарного; карточка обязана показывать payload (точное действие, дифф, риск, обратимость) —
  «одобрение со скрытым payload — антипаттерн».
- **Энфорсмент вне модели** (HumanLayer): гейт на уровне инструмента отправки, не инструкции в
  промпте — ровно I4 (fail-closed) отчёта 13.
- **Аудит-трейл включая отказы** (кто/когда/что/почему; версия политики) — git + блок решения в
  документе дают это бесплатно.
- **Таймауты и накопление:** запрос не висит бесконечно и не самоодобряется; батч-ревью цельных
  единиц против approval fatigue (I7 отчёта 13 — то же); метрики здоровья гейта (overturn rate,
  доля эскалаций) — кандидат в /experience.
- **Уведомления на Windows:** hooks Claude Code (Notification/Stop) + PowerShell BurntToast —
  системный тост со звуком без внешних сервисов; разные звуки «нужно решение» vs «готово».

**Вывод для D:** инварианты отчёта 13 совпадают с индустриальным консенсусом («долговечный
документ-предложение + явное решение + аудит-запись» = md в git — родная стихия KAIF); методология
2.1 фиксирует инварианты и контракты имён, реализацию строит проект.

### 11.3 Watchdog/heartbeat (→ эпик G)

- **Сторож обязан быть внешним**: «the thing that runs tasks shouldn't also judge if they're
  healthy» — зависший исполнитель не выполнит свой self-check. Подтверждает постановку владельца
  (локальные код-механизмы дёргают агента).
- **Heartbeat-файл + порог свежести**: агент после каждой итерации дописывает строку
  «timestamp | задача | статус | next»; сторож проверяет mtime (боевой паттерн 24/7 Claude-агента,
  launchd). Пульс пишется по факту завершённого шага, НЕ по таймеру (антипаттерн fire-and-forget).
- **Рестарт с recovery-контекстом**, не «голый» — у KAIF это /resume + STATUS.md бесплатно.
- **Dead man's switch** (healthchecks.io-модель): ждать пингов успеха, тревожиться по отсутствию;
  grace time; **политика рестартов**: cooldown, лимит ~3 попыток, дальше эскалация человеку —
  никогда «always restart» (crash-шторм).
- **Пороги из измеренных длительностей**, не с потолка (антипаттерн timeout auctions); дебаунс на
  долгие сборки; single-instance guard у сторожа (lock-файл) против двойных рестартов.
- **Пульс-промпт** (OpenClaw): периодический дешёвый ход «если всё тихо — HEARTBEAT_OK», тик
  откладывается при занятости; один слой планирования (не cron поверх встроенного heartbeat).

**Вывод для G:** методология = канон heartbeat-файла в автоциклах + опциональный внешний сторож
(Планировщик задач Windows / cron + скрипт проекта) + политика рестартов md-правилом. KAIF здесь
не может остаться чисто-markdown — внешний слой неизбежен, но он опционален и локален.

### 11.4 Статус-документы и летопись (→ эпики H и F)

- **Diátaxis:** документ, смешивающий режимы читателя (справка vs понимание vs история), не
  работает ни для кого — разделение STATUS/HISTORY канонично, не оверинжиниринг.
- **ADR (Nygard):** «Large documents are never kept up to date. Small, modular documents have at
  least a chance» — летопись = append-only маленькие записи; отмена — через supersede, не правку
  задним числом.
- **Google docguide:** документация — «бонсай»: минимально жизнеспособная, мёртвое удаляется,
  обновление в том же коммите; устаревший док вреднее отсутствующего.
- **Паттерн Node.js** для разросшейся летописи: корневой файл — короткий индекс, история — по
  файлам линий версий + ARCHIVE.
- **Правило размера — не лимит строк, а тесты**: «уберу строку — следующий агент ошибётся?»
  (официальные доки Claude Code про раздутый контекст: «bloated files cause ignoring actual
  instructions») + «новичок читает целиком за один присест» (ориентир Nygard: 1–2 страницы).
- **Release notes vs README vs changelog** (Keep a Changelog / Common Changelog / LaunchNotes):
  changelog — полный техреестр по версиям; ноты — курируемый нарратив дельты релиза; README —
  продукт в настоящем времени. Подтверждает правило владельца (п. 8) дословно.

**Вывод для H:** STATUS = living-сводка с тестом «уберу — сломается?», вытеснение закрытого в
PROJECT_HISTORY на каждом /end-chat («стрижка бонсая»); HISTORY = append-only летопись, правка
задним числом запрещена; при разрастании — резка по линиям версий с индексом.
