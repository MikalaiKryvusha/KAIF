## §2. Эпик K — интерактивный контур (пп. 1.0–1.12 кроме 1.11)

**Вес: самый тяжёлый эпик релиза** (владелец о 1.7: «КРИТИЧЕСКОЕ, ТЯЖЕЛЕЕ ВСЕГО ОСТАЛЬНОГО В ЭТОМ
СПИСКЕ»). Тест тяжести: трогает ≥3 подсистемы (owner-reviews · interview · AGENT_GUIDE ·
PHILOSOPHY · TESTING) · внешняя правда (4 полевых источника из 3 проектов) · больше одной сессии ·
решения владельца (имя, поставка, дефолты) — 4 из 5 критериев.

**Четыре независимых полевых источника сходятся в один норматив:**

1. **`ndim/researches/28`** (394 строки, Opus 5, NDim) — исполнимый контракт «как построить»
   (часть II): состав поставки 4 инструмента + ядро (~1700 строк, ноль зависимостей), контракт
   нормализации и хеша (`normalizeText` = снять BOM → CRLF/CR→LF → снять хвост → ровно один \n;
   «четыре "лица" одного текста дают ОДИН хеш»), 5 полевых правил разбора документа, устройство
   страницы (виджет вопроса с полосой состояния, обе темы ОС, снятие выбора через mousedown-механику,
   встроенная медиа data:-URI/srcdoc), запись решения в ТРИ места, гейт отправки fail-closed
   («отправщик отказывает даже под явным --apply»), сигнал (звук первым и всегда; голос — параметр
   с честным откатом), накопление + инвариант «сохранение будит ждущего», QA-прогон живым браузером
   11 блоков + 5 мутаций. Цена для планирования: одна сессия работы, 118+40 проверок, 7 дефектов
   реализации (3 пойманы только живыми данными, 2 — глазами владельца).
2. **`unliminiumProject/bugs/54`** — И1–И5 с готовой починкой и headless-рецептом проверки «убить
   сервер → кликнуть → прочитать DOM» (эталонные замеры до/после в документе бага).
3. **`reports/25`** — И9–И12 с замером по трём проектам (124/227 = 55 % ответов без
   единой ссылки вне interviews/; интервью-сирот НОЛЬ — дефект живёт на уровне вопроса) и
   референсом `questions-guard.mjs` половина 3 (базовая линия долга, двуплечий итог, доказан
   мутацией). Плюс `ndim/bugs/112` — И13–И15 (провенанс двумя представлениями, местное время,
   вырезание HTML-комментариев; фикс в одном узле `mdToHtml`, нулевая миграция архива).
4. **GitHub issue #2** (Nogamelabs, ВТОРОЙ отчёт того же контура, 2026-08-06, статус OPEN) — сверх
   скоупа: именованный класс требований **«обращение с работой человека»** («проверяется не
   самотестами, а перечнем оплаченных полем случаев»); **симметричный обратный пульс** («если
   контур умеет замечать смерть партнёра в одну сторону — обязан замечать и в обратную» — сервер
   замечает закрытую страницу; отработал в поле); 19 требований A1–D6; три исхода ожидания
   («решение записано · страница закрыта без ответа · прервано человеком; "он, наверное, ещё
   думает" — не исход»); страж СОДЕРЖАНИЯ вопроса с обязательной оговоркой «объявление намерения»
   (`<!-- new: … -->` — иначе страж «запрещает спрашивать про будущее»); приёмка по ЖИВЫМ
   документам с независимым признаком («39 фикстурных проверок → 0 находок; первый прогон по 16
   живым документам → 2 настоящие потери»); каталог платформенных ловушек Л1–Л8; чек-лист приёмки
   6 пунктов; принцип «ложная тревога опаснее пропуска». Комментарий 1 прямо просит: сводить его с
   пп. 1.7/1.8 «вместе, а не как два независимых входа» — этот эпик так и делает.

**Главная архитектурная развилка внутри эпика — единая нумерация инвариантов.** В навыке
`/owner-reviews` уже живут I1–I7 (2.1, оттрассированы к отчёту 13 Nogamelabs). Скоуп добавляет
И1–И15 в СВОЕЙ нумерации, отчёт NDim предлагает «сохранение будит ждущего» как I8 — который
коллидирует с И8 скоупа (механический греп показа). Решение эпика: единое пространство номеров
I1–I2x строится в фазе K1 с явной картой соответствия «номер скоупа → канонический номер»; два
разных «I8» в одном регламенте не живут. Инварианты-антагонисты записываются РЯДОМ с явной
оговоркой: «сохранение будит ждущего» (процесс умирает ПО СОБЫТИЮ) провоцирует ложную симметрию
«пусть умирает и по часам» — а «терпение машины бесконечно» это запрещает; третья грань от
issue #2: бесконечное терпение верно, только пока жив адресат (обратный пульс).

**Три слоя эпика** (граница «KAIF документирует методологию, не проектирует инструменты»
сохраняется, но по указанию владельца контракт сборки становится РАДИКАЛЬНО конкретнее):
- **Норматив** — инварианты + класс требований «обращение с работой человека» (canon,
  /owner-reviews + /interview + AGENT_GUIDE для показа И6–И8);
- **Исполнимый контракт сборки** — пошаговый рецепт из части II отчёта NDim (порядок шагов
  обязателен, «каждый следующий шаг опирается на предыдущий»), спецификация элементов страницы,
  сигнала (три писка — частоты снять с реализации NDim `tools/review.mjs`: в отчёте их НЕТ, в
  скоупе названы 880/660/990 Гц — сверить с кодом), каталог ловушек, чек-лист приёмки;
- **Стражи и приёмка** — страж места вопросов + страж обратного плеча (baseline долга, двуплечий
  итог) + детектор протухшего статуса + страж содержания вопроса + headless-проверка мёртвого
  сервера + греп показа-ссылкой; каждый страж доказан мутацией (норма §9).

**Гейт приёмки эпика:** ВЫПОЛНЕННОСТЬ 11 условий закрытия issue #2 (все 19 требований A–D,

## §4. Эпик M — контур обратной связи (пп. 8, 10, 11, 14 + 1.11)

Цель владельца дословно: «формируем так называемый "A closed-loop feedback system"» — агенты
работают по KAIF → сами находят упущения ФРЕЙМВОРКА → оформляют «вектора ошибки» (тикеты
origin + `/bugs/KAIF`) → ИИ-агент-разработчик KAIF вырабатывает управляющее воздействие →
следующая версия уменьшает ошибки в поле. Владелец просит изучить матчасть: принципы САУ +
Полная функция управления (ДОТУ) — «пропитать KAIF в тех частях, которые касаются замкнутых
циклов самоуправления, стратегическо-тактическо-операционного планирования».

Состав:
- **Протокол «баг/запрос KAIF»** (п. 8): режим 8.1 (origin-привязка: разведка в
  `/bugs/KAIF` И в origin issues через gh; дописать воспроизведение ИЛИ завести тикет по канону
  багов) и режим 8.2 (аноним: только локальный `/bugs/KAIF`). Новая каноническая директория
  `/bugs/KAIF`.
- **Контур «дефект в САМОМ KAIF»** (п. 1.11, решение владельца NDim дословно в скоупе): пять шагов
  (доказать КЛАСС по соседним проектам, читая не правя → починить ЛОКАЛЬНО механизмом с мутацией,
  не дожидаясь апстрима → развёрнутый отчёт с исполнимым контрактом → пункт в актуальный
  `*_scope.md` → замкнуть у себя). В NDim уже в AGENT_GUIDE; в нашем payload — НЕТ (gap-анализ:
  греп 0 совпадений). Пункты 1.9/1.10 — первый полный полевой проход этого контура.
- **Канон-директория `reports/`** (п. 10) + поддиректории `reports/KAIF_UPDATES` (п. 11),

  судьи поймали major-находки).
- **Соглашение о принципах** (п. 14): агентам дано явное распоряжение смело предлагать новые
  проверенные боем методологии И рекомендовать отказ от неработающих; канал — тот же контур

Пять пунктов владельца об одном: документы KAIF становятся ПРОВЕРЯЕМЫМИ и САМООПИСАННЫМИ.

- **Вектор цели + критерии приёмки на первом месте** (п. 13) — во все ЦЕЛЕВЫЕ документы (баги,

## §9. Сквозные инварианты 2.2 (действуют на каждый эпик)

Выведены из пересечения ≥2 независимых источников (полевые отчёты + EXPERIENCE):

1. **Каждый новый страж доказан мутацией ДО доверия** — «половина написанных стражей не умела
   краснеть, пока их не проверили мутацией» (отчёт 25; тот же урок в bugs/112, issue #2,
   EXP-0016/0017). Мутация с ПРЕДСКАЗАНИЕМ результата до прогона (NDim-метод).
2. **Страж считает свою точность; ложная тревога опаснее пропуска** — она приучает игнорировать
   вывод (issue #2 — поднять до принципа; классы L-5/L-6: шум 19 %-точности и 218 «ABSENT»
   «дрессируют оператора игнорировать аудит целиком»).
3. **Метрики петель — двуплечие** — «ждут владельца 0» при 36 неразнесённых ответах = ложный
   зелёный; любой итог стража докладывает ОБА плеча; у любой петли проверяются оба плеча
   («получить ответ — не значит разнести его»; «место артефакта ≠ доставка ценности»).
4. **Страж, красный с рождения, приучает себя игнорировать** — базовая линия унаследованного
   долга (baseline), красный только на НОВОЕ, число долга печатается и обязано убывать.
5. **Зелёное без содержания хуже красного** — ненастроенный страж не exit 0, а «SKIPPED» с
   отдельным кодом; счётчики считают ЗАПИСЬ, не намерение (класс L-4).
6. **Новая канон-сущность = полный круг регистрации доставки** (сборка · манифест · карта
   модулей · README · help-kaif · CLAUDE.md · языковые пакеты · полигон) — EXP-0003 + инвариант 2
   плана 22; в 2.2 новых сущностей много: reports/, bugs/KAIF, REQUIREMENTS_FRAMEWORK,
   портрет-файл, переименованные навыки.
7. **Обещания релиза = код** — линт бандла перед релизом (пары «документ ↔ ведущий навык»,
   нормы нот против шаблонов); класс L-7/L-8 «обещанный guard не существует» не повторяется.
8. **Правило-как-проза не работает — точка решения, поле шаблона или страж** (EXP-0001/0002;
   «проза в хвосте длинного скилла слабой сессией не исполняется» — так родилась дыра 1.9).
9. **Чужие выверенные тексты вендорить дословно** (EXP-0006): исполнимый контракт NDim,
   инварианты, формулировки владельца — с атрибуцией и помеченными патчами, не парафразом.
10. **Опциональность**: новые режимы — опциональный сахар; развёртывание без них не краснеет
    (принцип 2.1, подтверждён полем).
11. **Кириллица (письмо владельца) не живёт в телах EN-шаблонов** — ослепляет сеть распознавания
    перевода (KLAS, класс L-1); примеры локализуемого — в языковые пакеты.

| **M. Контур обратной связи** | bugs/KAIF + origin issues + reports/ + обязательные отчёты + «дефект в САМОМ KAIF» + соглашение о принципах; матчасть ДОТУ | 8, 10, 11, 14, 1.11 | тяжёлый | `plans/29_EPIC_…M…` |
| **N. Канон-архитектура** | REQUIREMENTS_FRAMEWORK (14-й док) + вектор цели/критерии приёмки + шапки-мета + таксономия + термин «контур» | 13, 15, 4, 18, 16 | тяжёлый | `plans/30_EPIC_…N…` |
| **O. Контекст и окружение** | механизм принудительного освежения (hooks/адаптеры) + досье окружения | 3, 7 | средний | `plans/31_EPIC_…O…` |
| **P. Переименование kaif-*** | схема имён + rename payload + rename-миграция update + зеркала | 6 | средний (механика + миграция) | `plans/32_EPIC_…P…` |

**Рекомендуемый порядок: L → K → M → N → O → P → Фаза R** (задачи T1–T7 — параллельно, в дырках):

- **L первым** — поле горит: парк владельца продолжает обновляться на 2.1, и каждое обновление
  платит когнитивный налог классов L-1…L-6 (прецедент: в 2.1 полевые фиксы B тоже шли первыми).
- **K вторым** — критичнейший блок скоупа (1.7 — «тяжелее всего остального»); его полевые
  контракты готовы и стандарта N не ждут.
- **M третьим** — замыкает петлю; его reports/ нужен задаче T3 и отчётам об обновлении.
- **N четвёртым** — REQUIREMENTS_FRAMEWORK и таксономия; альтернатива «N до K» (сначала
  дисциплина требований, потом большой K по ней) отклонена: K пишется по готовым полевым
  контрактам, а держать критический блок в очереди ради церемонии — против Парето; сами планы
  2.2 уже написаны с векторами цели и критериями приёмки (дисциплина п. 13 применена досрочно).
- **O пятым** — зависит от яруса «перечитывания» таксономии N.
- **P предпоследним** — одним скриптовым проходом по готовому дереву 2.2 (см. §7), затем Фаза R.

Зависимости: T3 после M (reports/) · O после N (ярус перечитывания) · P после всех содержательных
(rename-проход) · T7 сшит с K (обе правки PHILOSOPHY) · K.dogfooding рендерит интервью 007.

## §11. Индустриальная разведка (гуглёж; 4 направления, по источникам)

### 11.1 Замкнутые контуры обратной связи (→ эпик M)

- **Циклы улучшения:** PDCA/Деминг (asq.org/quality-resources/pdca-cycle) — «Act» замыкается
  обратно в «Plan», петля непрерывна; OODA Бойда (en.wikipedia.org/wiki/OODA_loop) —
  критический этап Orient: накопленный опыт определяет, во что превращаются наблюдения (роль
  EXPERIENCE.md). Теория управления для софта (SEAMS 2015, dl.acm.org/doi/10.5555/2821357.2821370;
  Springer 978-3-642-02161-9_3): петля обратной связи — **первоклассный архитектурный элемент**;
  индустрия обходится простейшими линейными регуляторами — «простой контур лучше отсутствующего
  идеального».
- **ДОТУ — полная функция управления** (первоисточник: ВП СССР, ред. 2011 —
  vodaspb.ru/arhive/vp_sssr/knigi/dotu_2011/dotu_a4_20110626.pdf; изложения:
  analitikishkola.ru/stati/pfu-v-zhizni, planet-kob.ru/articles/8405): **7 этапов** —
  (1) опознавание фактора среды → (2) стереотип распознавания на будущее → (3) вектор целей →
  (4) концепция управления → (5) управляющая структура → (6) контроль → (7) ликвидация/поддержание
  структуры. *[Поправка фазы M1, 2026-08-07: сверка с самим PDF показала — в Таблице 1 ред. 2011
  этапов ВОСЕМЬ: 7-й — «совершенствование действующей концепции», 8-й — ликвидация/поддержание;
  7-пунктовый перечень с ликвидацией седьмым — сжатый пересказ раздела 13 (стр. 80–81). Дословно —
  `researches/18` §1.1.]* Терминология: **вектор целей** (иерархия желаемого по важности) · **вектор текущего
  состояния** · **вектор ошибки** (разность; качество управления оценивается по нему) · схемы:
  программная / программно-адаптивная / **предиктор-корректор** (управление по прогнозу).
  Соответствие эпику M прямое: полевой дефект = фактор среды (1); класс/fingerprint = стереотип
  (2); желаемое поведение фреймворка = вектор целей (3); правка канона = концепция (4); контуры
  репортинга = структура (5); аудиты = контроль (6).
- **SRE-петли:** blameless postmortem (sre.google/sre-book/postmortem-culture) — системные
  причины, не виновные; error budget (sre.google/sre-book/embracing-risk) — «допустимый вектор
  ошибки» индустриально; судьба action items (usenix.org …login_spring17_09_lunney.pdf) —
  **<40 % пунктов закрывается за 90 дней**, если они живут в документе постмортема, а не в
  рабочем беклоге с владельцем и каденцией.
- **Полевые отчёты в опенсорсе:** Kubernetes triage (`needs-triage` по умолчанию, явное
  `/triage accepted` — kubernetes.dev/docs/guide/issue-triage); VS Code (боты, canned responses);
  Rust RFC — тяжёлый процесс ТОЛЬКО для substantial-изменений (rust-lang.github.io/rfcs).
  Дедупликация на масштабе: Windows Error Reporting — бакеты по сигнатурам + **progressive data
  collection** (sigops.org …glerum-sosp09.pdf); Sentry fingerprint-правила
  (docs.sentry.io/concepts/data-management/event-grouping/fingerprint-rules).
- **Агенты и фидбек об инструменте:** Claude Code `/bug` — автозахват версии/платформы в
  предзаполненный issue (github.com/anthropics/claude-code); Reflexion (arxiv.org/abs/2303.11366)
  — текстовая память об ошибках улучшает замороженную модель (наука за EXPERIENCE.md).
  **Честный пробел:** прецедента «агент АВТОНОМНО заводит issue о дефекте своего фреймворка» не
  найдено — KAIF здесь впереди индустрии.
- **Антипаттерны:** 🔴 **curl закрыл bug bounty из-за ИИ-слопа** (~20 % подач — слоп,
  подтверждаемость упала с 15 % до <5 % — bleepingcomputer.com …curl-ending-bug-bounty…) —
  контур «агент сам заводит issue» без гейта качества У ОТПРАВИТЕЛЯ дискредитирует канал;
  stale-боты (nostalebots.xyz — «issues не портятся от времени»); Гудхарт (KPI на число
  багов/закрытий сожрёт сигнал); телеметрия без согласия (Audacity 2021); постмортем-полка.

**Вывод для M:** вектор целей/ошибки формализовать по ДОТУ + error budget; fingerprint-сигнатура
дефекта ({документ/навык · класс симптома · версия KAIF}) + обязательный греп bugs/ и issues ДО
заведения (совпадение = «+1 наблюдение», не новый тикет); в апстрим — только с воспроизведением
или дословной цитатой (урок curl; планка CHIA «снижать нагрузку мейнтейнера»); пункты петли —
в общий беклог с владельцем; blameless-рамка (провал слабой модели = сигнал о недостающем
гвардрейле); прозрачность вместо телеметрии (отчёт всегда файл в репозитории проекта, явное
действие); шаблон отчёта с автозахватом из `.kaif/kaif.json`.

### 11.2 Инженерия требований и мета документов (→ эпик N)

- **ISO/IEC/IEEE 29148:2018** (iso.org/standard/72089.html; дистилляция —
  modernrequirements.com/blogs/iso-29148-explained): 9 характеристик требования (necessary ·
  appropriate · unambiguous · complete · singular · feasible · verifiable · correct ·
  conforming) + 5 характеристик набора. Список владельца в идее 20 — ровно эта таксономия.
- **NASA SE Handbook, Appendix C** (nasa.gov/reference/appendix-c-how-to-write-a-good-requirement):
  shall/will/should-дисциплина + **явный чёрный список непроверяемых слов** («flexible», «easy»,
  «as appropriate», «etc.», «user-friendly») — идеально греп-линтуемо.
- **Fit criterion** (Volere — volere.org/templates) — каждое требование несёт измеримый критерий
  соответствия; **Planguage Гилба** (accu.org …gilb_299) — триада Scale/Meter/Target для
  числовых критериев.
- **EARS** (alistairmavin.com/ears) — 5 паттернов (Ubiquitous/WHEN/WHILE/IF-THEN/WHERE);
  **стандарт де-факто для ИИ-агентов**: AWS Kiro генерирует requirements.md в EARS
  (kiro.dev/docs/specs/feature-specs). RFC 2119/8174 — нормативная модальность только явными
  ЗАГЛАВНЫМИ ключевыми словами.
- **Шапки-мета:** ADR Нигарда (Status: proposed→accepted→superseded by NNN; устаревшее НЕ
  правится — надстраивается с двусторонней ссылкой); MADR (YAML-мета); RFC 7322
  (Obsoletes/Updates — машинный граф замещения); Dublin Core (Relation); YAML-frontmatter с
  ФИКСИРОВАННОЙ схемой и валидацией (docs.github.com …using-yaml-frontmatter).
- **Машинная проверяемость:** requirements smells (Femmer et al., arxiv.org/pdf/1611.08847 —
  смеллы выведены ИЗ критериев 29148, детектятся словарями); NALABS (arxiv.org/pdf/2202.05641);
  LLM-судья требований по 29148 (arxiv.org/pdf/2408.10886); Vale/markdownlint-конвейер.
  **Spec-driven development:** GitHub spec-kit (github.com/github/spec-kit — Constitution →
  Specify → Clarify → Plan → Tasks; «constitution» = прямой аналог канона KAIF; Clarify =
  /interview).
- **Антипаттерны:** BDUF (вся спека заранее); **Definition of Ready как шлюз-гейт** (мини-водопад
  — scrum.org …lead-anti-patterns); MoSCoW-гравитация «всё — Must»; мёртвая спецификация (Gojko:
  живёт только регулярно исполняемая); тяжёлый ALM (DOORS-класс) — ниша requirements-as-code
  выросла как отказ от него; нелинтуемая мета гниёт.

**Вывод для N:** ядро REQUIREMENTS_FRAMEWORK.md = таксономия 29148 (список владельца
канонизировать со ссылкой на стандарт) в дистилляции NASA Appendix C + **чёрный список
непроверяемых слов RU+EN** (греп-страж — родная механика KAIF); EARS-паттерны с русифицированными
ключевыми словами как нотация формулировки; формула критерия приёмки = fit criterion (+ триада
Гилба для числовых); шапка-мета = **6–8 полей фиксированной YAML-схемой** (status · date · goal ·
verify · supersedes/superseded_by …), правило «каждое поле либо линтуется, либо не нужно»;
жизненный цикл — supersede, не правка; критерии качества работают линтером и рубрикой судьи,
НЕ шлагбаумом перед началом работы (антипаттерн DoR).

### 11.3 Освежение контекста и досье окружения (→ эпик O)

- **Claude Code hooks** (code.claude.com/docs/en/hooks — проверено живым fetch): `SessionStart`
  (матчеры `startup|resume|clear|compact`; возвращает `additionalContext`; `compact` = «перечитай
  канон после сжатия»); `UserPromptSubmit` (впрыск на каждый промпт — точка для stateful-таймера
  «>60 мин с последнего освежения»); `PostToolBatch` (периодические напоминания в длинных
  автономных прогонах без промптов); `Stop` (`decision: "block"` — страж «не завершайся, пока
  STATUS не обновлён»); `PreCompact`/`PostCompact`; `FileChanged`/`watchPaths` (следить за самим
  каноном). Кап `additionalContext` — 10 000 символов → **впрыскивать приказ перечитать, а не
  документы**.
- **System-reminder паттерн** (michaellivs.com/blog/system-reminders-steering-agents): в Claude
  Code ~37 напоминаний; принцип «nudging beats forcing» — жёсткие ограничения живут в дизайне
  инструментов, напоминания подталкивают.
- **Аналоги:** Cline Memory Bank (docs.cline.bot/best-practices/memory-bank — иерархия файлов +
  правило «читать ВСЕ в начале КАЖДОЙ задачи»; эволюция в lifecycle-хуки:
  hindsight.vectorize.io …cline-persistent-memory — «There's no MCP tool the model can forget to
  call»); Cursor rules (`.cursor/rules/*.mdc`, `.cursorrules` задепрекейчен; always-правила
  <200 слов — token tax); **AGENTS.md** (agents.md — стандарт 60 000+ проектов, поддержан 20+
  агентами; чистый markdown без энфорсмента); Windsurf (лимиты 6k/12k символов).
- **Наука об угасании следования:** context rot (research.trychroma.com/context-rot — деградация
  задолго до переполнения окна); lost in the middle (arxiv.org/abs/2307.03172 — U-кривая);
  мультитёрн −39 % (arxiv.org/abs/2505.06120); IFScale (arxiv.org/pdf/2507.11538 — плотность
  инструкций сама разрушает следование); **DriftBench** (arxiv.org/pdf/2604.28031 — модель
  ДОСЛОВНО ПЕРЕСКАЗЫВАЕТ ограничение, которое нарушает: recall ≠ adherence). Anthropic context
  engineering (anthropic.com/engineering/effective-context-engineering-for-ai-agents) —
  structured note-taking = ровно модель KAIF.
- **Окружение:** devcontainer.json (containers.dev/implementors/spec) — декларативное
  машиночитаемое описание среды; 12-factor dev/prod parity («tiny incompatibilities crop up»);
  **ansible facts** (spacelift.io/blog/ansible-facts) — структурированный инвентарь хоста,
  снимаемый заново каждый прогон.
- **Антипаттерны:** напоминание в прозе (DriftBench + Cline: инструкцию можно забыть исполнить);
  монолитный always-on файл правил; гигантская вечно-загруженная память (Cline ~300K токенов);
  автовпрыск полных документов; частые напоминания без cooldown; протухшая память без пометок
  давности.

**Вывод для O:** **двухконтурная архитектура** — markdown-ритуал обязателен (ядро KAIF, работает
везде) + опциональные hook-конфиги в поставке для систем, где хуки есть (путь Cline: проза →
хуки); конкретные хуки поимённо (SessionStart/compact · UserPromptSubmit-таймер · PostToolBatch ·
Stop-страж); **напоминание = проверяемое действие** (обнови timestamp-маркер, процитируй пункт
плана — иначе recall без adherence); nudging, не forcing (блокирующий exit — только стражам
целостности); досье окружения — по образцу ansible facts: машиночитаемо, ДАТИРОВАНО, с командой
перегенерации и staleness-правилом («факты старше N недель — гипотеза»); критическое — в начало
документа И кратким чек-листом в конец (lost in the middle); AGENTS.md-витрина — дёшево.

### 11.4 Агентное ревью и аудит кодовой базы (→ задача T3)

- **Cloudflare security-audit-skill** (github.com/cloudflare/security-audit-skill;
  blog.cloudflare.com/build-your-own-vulnerability-harness): фазы Recon → Hunt → **Validate
  (проверяющий агент НИКОГДА не тот, кто нашёл)** → Report (человеческий + машинный); «весь
  дизайн исходит из того, что агент будет галлюцинировать»; severity = impact × likelihood;
  **один прогон находит ~половину** — нужны серии.
- **Anthropic claude-code-security-review** (github.com/anthropics/claude-code-security-review):
  выделенный этап фильтрации FP + **жёсткий список исключённых шумных классов** (DoS,
  rate-limiting, generic validation…).
- **Tricorder/Google** (cacm.acm.org/research/lessons-from-building-static-analysis-tools-at-google):
  **effective false positive** — находка, по которой разработчик не предпринял действий;
  **порог доверия ~10 %** — шумнее → инструмент отключают; лучший отчёт — с приложенным фиксом.
- **Copilot Autofix** (github.blog …found-means-fixed): находка с эскизом фикса и проверкой
  чинится «слабым исполнителем» в 2/3 случаев без доработок — прецедент handoff
  «сильный аудитирует → слабый чинит».
- **Форматы:** SARIF 2.1.0 — разделение rule/result + **baseline** (новая/известная находка);
  CWE-семейства (pillar→class→base→variant); CVSS → дополнен SSVC-решениями Act/Attend/Track
  (picussecurity.com …from-scores-to-security-proof).
- **Наука:** CodeX-Verify (arxiv.org/pdf/2511.16708 — условно-независимые верификаторы находят
  больше суммы одиночных); HalluJudge (arxiv.org/html/2601.19072 — **галлюцинированная находка
  звучит убедительнее настоящей**; без цитаты и репро тон побеждает факт).
- **Антипаттерны:** curl/AI-slop (см. 11.1); recall без среза шума (Greptile: 30–50 % находок в
  ручной триаж — команды тонут); самопроверка находителем; «теоретические» находки без сценария;
  один прогон = полный аудит; раздутые инструкции ревьюеру (часть молча игнорируется — Copilot).

**Вывод для T3:** текущий `/code-revision` уже совпадает с фронтиром в главном (оси + скептик с
дефолтом «не дефект» + цитата-контракт) — **достраивать, не ломать**: явная Recon-фаза + секция
«Скоуп и методология» в отчёте (что смотрели, каким срезом, на каком коммите, какой моделью);
двухслойный отчёт (executive для владельца + технический для исполнителей), группировка **по
семействам** (CWE-манера, локальная таксономия проекта); **схема находки = контракт слабого
исполнителя** (цитата+строки · конкретный сценарий провала · impact×likelihood + SSVC-решение ·
эскиз фикса · машинно-проверяемый критерий приёмки фикса · границы «чего не трогать»); baseline
против bugs/ и EXPERIENCE (дедупликация обязательна); серии прогонов с фиксацией покрытия;
детерминированный слой (стражи/грепы) ПЕРВЫМ, повторяющаяся LLM-находка конвертируется в новый
греп-страж; метрика здоровья — effective-FP ≤ ~10 %.
