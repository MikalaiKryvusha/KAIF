## 2. Источник класса — агент проверяет в контексте, которого у пользователя не бывает

**Формула класса.** Проверка агента (смоук, e2e, зонд, приёмка) ходит в СТЕРИЛЬНОМ контексте, который
агент строит из ничего: свежий браузер без маркеров и памяти, чистый чекаут, пустая база, «сегодняшняя»
сборка, широкий экран, быстрая сеть, локальный эмулятор. У настоящего пользователя контекст всегда НЕ
пустой: он приходит С ИСТОРИЕЙ — маркер сессии в `localStorage`, память темы/языка, кеш HTML прошлой
сборки, вкладка, открытая через выкат, узкий экран, данные в боевой форме, время суток. Дефект живёт ровно в
разности этих контекстов, и все приборы агента зелены по построению — они не могут увидеть состояние,
которого у них нет.

**Почему агент так делает (три корня, все — свойства агента, не проекта):**

1. **Стерильность = воспроизводимость.** Канон тестирования учит «свежий контейнер/каталог» (гейт 2
   `TESTING_FRAMEWORK`: «поставленный артефакт обязан стартовать в изоляции»), фикстуры — из `mkdtemp`,
   контексты Playwright — новые (`browser.newContext()` — инкогнито по построению). Это ПРАВИЛЬНО для
   вопроса «стартует ли продукт», и ЛОЖНО для вопроса «что увидит человек, который уже был здесь».
   Агент переносит первое правило на второй вопрос, потому что второй вопрос нигде не задан.
2. **Агент — всегда новый посетитель.** У сессии нет истории в браузере, нет вчерашней вкладки, нет кеша:
   она физически не может «прийти снова». Единственный носитель возвращающегося состояния — владелец, и он
   находит дефект «через минуты после выката» (#52, `bugs/124`, `bugs/40` — все три найдены владельцем).
3. **«Отрисовано» судится присутствием, а не видимостью.** Ассерт «элемент есть в DOM» (или даже
   `toBeVisible()` — непустой bounding box) зеленеет под непрозрачным щитом, оверлеем, петлёй редиректов
   (§4.3). Агент видит DOM, человек видит пиксели.

**Границы класса.** Это не «мало тестов» и не «плохой смоук»: у проекта #52 смоук под сессией 24/0 и
гостевой 81/81 были зелёными и честными. Это класс **контекста проверки**: смоук отвечал на вопрос,
которого не задавали, — и зелёный был доказательством не о продукте, а о стерильном контексте (та же
мысль, что гейт 6: «неаутентифицированный смоук — НЕ улика о продукте»; класс шире — ЛЮБОЙ смоук без
состояния реального посетителя не улика о том, что видит посетитель). Родня в каноне: «стенд зелен при
любом коде» (EXP-0114 поля), гейт 6 №18 («три выката за ночь отдали приложение, которое не стартовало, при
зелёных локальных приборах»).

## 4. Как держит класс индустрия (источники — по поиску 2026-09-05; чтение, без вендорной привязки)

1. **Состояние посетителя как ФИКСТУРА — persona/storage state.** Стандартная практика e2e: залогиниться
   один раз, сохранить `storageState` (cookies · `localStorage` · `sessionStorage` · IndexedDB) в файл и
   стартовать каждый тест УЖЕ с этим состоянием; несколько ролей = несколько файлов состояния; сеять
   пользователя и токен через API и впрыскивать в контекст напрямую, минуя UI-логин
   ([BrowserStack — storageState](https://www.browserstack.com/guide/playwright-storage-state),
   [Checkly — shared storageState](https://www.checklyhq.com/blog/speed-up-playwright-tests-with-storage-state/),
   [scrolltest — API seeding](https://scrolltest.com/playwright-database-seeding-e2e-api/)). Индустрия
   решает это как ускорение; для нашего класса та же механика — **единственный способ дать прибору
   контекст возвращающегося**: маркер и память кладутся в контекст напрямую, без полного входа (ровно так
   починил себя проект #52).
2. **Холодный и тёплый проход — два разных замера.** Перф-методология браузеров различает *cold* (свежий
   контекст) и *warm* (повторная загрузка того же адреса) и гоняет ОБА — «chimera»: холодный проход,
   переход, повторная загрузка ([Mozilla Raptor metrics](https://github.com/mozilla/gecko-dev/blob/9a83c0336f00635d8253ca920d3319c6936cde12/testing/raptor/raptor/perfdocs/metrics.rst));
   синтетические мониторы намеренно ходят свежим контейнером «мимо кеша» — и потому НЕ видят того, что
   видит RUM у реальных людей ([New Relic — synthetic smoke](https://newrelic.com/blog/how-to-relic/smoke-testing-with-synthetic-monitors));
   тестерам прямо говорят: инкогнито отключает кеш, а «в большинстве случаев очистка кеша ЧИНИТ проблему»
   — значит, проблема живёт у тех, кто кеш не чистил ([Ministry of Testing — browser cache basics](https://www.ministryoftesting.com/insights/browser-cache-basics-for-software-testers),
   [The Green Report — caching in automation](https://www.thegreenreport.blog/articles/cache-me-if-you-can-handling-caching-in-automation-testing/cache-me-if-you-can-handling-caching-in-automation-testing.html)).
3. **«Видно» ≠ «есть в DOM».** `toBeAttached` — присутствие; `toBeVisible` — непустой bounding box и не
   `visibility:hidden`; и даже `isVisible()` возвращает true для элемента, ПОЛНОСТЬЮ перекрытого другим
   ([Playwright assertions](https://playwright.dev/docs/test-assertions), [issue #9923](https://github.com/microsoft/playwright/issues/9923)).
   Перекрытие ловит только actionability-проверка действия (hit target при `click()`,
   [Playwright auto-waiting](https://playwright.dev/docs/actionability)) или снимок пикселей. То есть
   «отрисовано» в индустрии судится либо ДЕЙСТВИЕМ (элемент — цель клика), либо КАДРОМ, но не ассертом
   присутствия — щит #52 прошёл бы `toBeVisible` целевого текста под собой.
4. **Выкат и те, кто уже здесь.** Класс «старый HTML → новые чанки → 404/падение у вернувшихся» описан
   как штатная беда SPA; лечения — контент-хеши + правильная пара заголовков (HTML `no-cache`, ассеты
   `immutable`), а для ОТКРЫТОЙ вкладки — второй эшелон: приложение узнаёт о новой версии и предлагает
   обновиться ([Hypefactors — busting chunk cache for active users](https://medium.com/hypefactors/busting-spa-chunk-cache-for-active-users-after-a-deploy-a9a06242edb1),
   [DEV — SPAs: have your cache and eat it too](https://dev.to/jamesthomson/spas-have-your-cache-and-eat-it-too-iel),
   [Servd — cache busting](https://servd.host/docs/cache-busting)). То есть индустрия знает ТРИ контекста
   выката: новый посетитель · вернувшийся с кешем · вкладка, открытая через выкат, — и для каждого свой прибор.

**Вывод по индустрии.** Ни один источник не предлагает «ещё один смоук»: везде состояние посетителя
становится ЯВНЫМ ВХОДОМ прибора (файл состояния, тёплый проход, hit-target/кадр, заголовки кеша). Класс
закрывается не количеством проверок, а **перечнем контекстов, который прибор обязан пройти**, — и этот
перечень у индустрии есть, а у канона KAIF (гейт 6: гость · вошедший) — только его половина.

## 5. Как чинить КЛАСС в KAIF — что обобщается, что остаётся полю

Обобщаемое (свойство агента, одинаковое в любом проекте) — **правило контекста проверки**:

- **(К1) Матрица контекстов посетителя — явный вход любой проверки «как пользователь».** Прежде чем красить
  зелёным дверь/смоук/приёмку, агент ПЕРЕЧИСЛЯЕТ состояния, с которыми приходит реальный посетитель этого
  продукта (минимум четыре, где применимо: первый визит · вошедший · **вернувшийся с сидированным
  состоянием** (маркер, память, кеш прошлой сборки) · **вкладка, открытая через выкат**), и для каждого либо
  прибор ходит С ЭТИМ состоянием (файл состояния/сидирование — §4.1, тёплый проход — §4.2), либо
  контекст названо как непокрытый в отчёте двери. Пустая матрица = смоук не о продукте (продолжение мысли
  гейта 6). Это правило про ПОВЕДЕНИЕ АГЕНТА: не «добавь тест», а «назови контексты до зелёного».
- **(К2) «Отрисовано» = ВИДНО.** Приёмка экрана судится тем, что видит человек: hit-target целевого
  элемента (действие), кадр/скриншот с проверкой, что над ним нет щита/оверлея/петли редиректов, «видно
  или увели внутрь за N с» — а не присутствием в DOM и не `toBeVisible` целевого текста (§4.3).
- **(К3) Снятие того, на чём стояли другие, — с грепа «кто на нём стоял».** Увод, редиректор, обработчик,
  вход, который другой код использовал как побочный шаг (в #52 — увод корня опускал щит), снимается
  только после переписи потребителей; строка в fable-цикле `AGENT_GUIDE` (шаг «действуй хирургически»).
- **(К4) Прибор под состояние — отдельный и дешёвый.** Класс чинится не одним «большим смоуком», а
  прибором на КАЖДОЕ состояние (заголовки кеша — HEAD-запросы; цепь щита — статический страж; вернувшийся
  — сидированный контекст): образцы поля §3 — как иллюстрация формы, не как поставка.
- **(К5) Охота судьи** «green door blind to the returning user / verification context ≠ visitor's
  context»: отчёт двери без матрицы контекстов или с ассертом присутствия вместо видимости — находка.

Остаётся полю (про конкретный стек, в канон не едет): `csr = false`/`onMount`, `data-booting`,
`ndim-session`, `firebase.json` headers, SvelteKit `updated`, конкретные e2e-файлы.

Где жить фиксу в KAIF (кандидаты — форма для развилки владельца, не решение): гейт 6 `TESTING_FRAMEWORK`
обоих слоёв (матрица контекстов + «видно»), строка К3 в fable-цикле `AGENT_GUIDE` обоих слоёв, охота
`/fable-judge` обеих копий, записи policy/notes 2.6; опционально — машинная половина: шаблон отчёта двери
выката с обязательной таблицей контекстов (`| контекст | как дано прибору | итог |`) и линт, красный на
отчёте двери без строки «вернувшийся», по образцу `kaif-scenario-lint` (SKIPPED без отчёта двери).

## 6. Развилка для владельца — интервью №026 (сценариями, №98)

Класс понят (§2) и подтверждён шестью инцидентами (§3); индустрия закрывает его явным перечнем контекстов
(§4). Решения, которые принимает только владелец: (а) имя и место фикса класса в 2.6 — канон-правило К1–К3
+ охота (текст) или канон + машинная половина (шаблон отчёта двери + линт); (б) версия — 2.6 (критерий 16) или
2.7. Варианты и цены — в интервью №026 (поднято страницей контура тем же ходом). До слова владельца —
ничего не кодируется (№103, EXP-0115).

## Решения, принятые агентом без владельца

1. Разведка соседей — ТОЛЬКО чтение имён и шапок багов одного проекта с публичным входом (`ndim`); проекты
   без веб-входа с состоянием у клиента названы «класс не применим», а не «чисто» (там нечему ломаться).
2. Индустрия снята четырьмя поисками (persona state · warm/cold · visible vs attached · cache busting) без
   вендорной привязки; ссылки — в §4, каждая читалась по сводке поиска, не целиком.
3. Формулировка класса — «контекст проверки ≠ контекст посетителя», а не «смоук возвращающегося»: второе —
   один из контекстов первого (слово владельца: чинить класс, не инцидент).
